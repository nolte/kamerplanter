- **Exporting and importing a tenant** (issue #2138, REQ-056 §8): a garden can now be saved as an archive and brought back as a **new** garden — into the same or another installation. The lead with management may export (`POST /api/v1/tenants/{slug}/exports`, also during the deletion grace period), or a platform admin (`POST /api/v1/admin/platform/tenants/{key}/exports`), each with a password confirmation; at most one export runs at a time (`409 EXPORT_ALREADY_RUNNING`) and at most `TENANT_EXPORTS_PER_DAY` (default `3`) per 24 hours. Every member with management gets an e-mail. The archive holds all domain data, the links between them, the photos and the members without e-mail addresses — no credentials, API keys, invitations, integration secrets or logs — and can be downloaded for 72 hours. Only a platform admin may import (`POST /api/v1/admin/platform/tenant-imports`): every record gets a new id, members are mapped by the e-mail addresses of existing accounts, and the admin sets their role, not the archive. An archive with foreign records, missing catalogue entries or a damaged file is refused with `422` without writing anything. The new garden stays unreachable until its last record is written (**being imported**), a failure part-way removes everything again, and an import that died is cleaned up hourly. Archives carry the installation's signature; `verified` tells whether an archive comes unchanged from here. Integration keys stay out, and every download is in the security log. New settings: `TENANT_EXPORTS_PER_DAY`, `TENANT_IMPORT_MAX_UPLOAD_MB` and `RATE_LIMIT_TENANT_IMPORT`. How large an archive may unpack is bounded by fixed limits (1 GiB, at most 128 MiB of it records, plus a compression ratio and a record count), independently of `TENANT_IMPORT_MAX_UPLOAD_MB`. The new garden's owner gets exactly the permissions the admin confirms, and deactivated accounts cannot be mapped. A single huge line or millions of small values are refused before they cost memory, and the target plan's member limit applies to the imported members too. If a failed import cannot be fully rolled back, the half garden stays unreachable, the import reports `cleanup_pending`, and the hourly job deletes it. Refused and failed imports are in the security log too, with the archive's SHA-256. An archive the new garden's plan cannot hold — more members, more storage or more photos per plant — is refused when the import is requested, with the quota's code (`MEMBER_LIMIT_REACHED`, `STORAGE_QUOTA_EXCEEDED`, `PHOTO_QUOTA_EXCEEDED`), without writing anything. With TimescaleDB the archive now carries the garden's sensor readings too (`timeseries/readings.csv`: raw values and hourly/daily values, only the garden's own, counted against the export's size limit and covered by the signature); the archive format stays `kamerplanter-tenant-export/1`, the import skips the file and reports its row count. New is `TENANT_EXPORT_SIGNING_SECRET`: a secret of its own for the archive signature (at least 32 characters; empty = derived from `JWT_SECRET_KEY` as before; optional in the Helm chart via `tenantExport.signingSecret`). The import now has its own upload limit `TENANT_IMPORT_MAX_UPLOAD_MB` instead of the general 26 MiB — this route only, at most up to `UPLOAD_SPOOL_BUDGET_MB` (about 51 MiB with the defaults); for exactly this path the Helm chart sets the limit of the frontend nginx and of an Ingress of its own, `tenant-import` (`tenantExport.importMaxUploadMb`). The runbook explains how to size `/tmp` for larger archives. Still open: loading the readings on import. The user interface exists: the **Export** tab in the garden settings and the **Imports** page in platform mode (you enter the member keys by hand). See [Exporting and importing a tenant](../deployment/tenant-export-import.md).
- **Plans and quotas per tenant** (issue #2142, REQ-056 §7): every tenant now has a plan (`plan_key`) that sets its quotas — members, service accounts, storage, photos per plant and the three daily AI budgets. Every tenant starts on the plan `standard`, where each quota follows the existing server setting; without further plans no limit changes, including one adjusted by environment variable. Platform admins create, change and delete plans through `/api/v1/admin/platform/plans` and assign them with `PATCH /api/v1/admin/platform/tenants/{key}` (`plan_key`); every change is written to the security audit. A lower quota removes nothing, it refuses only the next creation. Every member reads plan and usage through `GET /api/v1/tenants/{slug}/entitlements`. The refusal codes stay the same. New is `TENANT_MAX_ORGANIZATIONS_PER_USER` (default `10`, `0` = only the operator creates organizations): the hard-coded limit of ten organizations per account is now configurable, the refusal now carries the code `ORGANIZATION_LIMIT_REACHED` instead of `VALIDATION_ERROR` (status still `422`), and an organization being erased (`deleted`) no longer counts. Note: in a plan, `0` means "unlimited" for storage and photos and "budget off" for the AI budgets; the plan response names such quotas in the field `unlimited`. Every quota has an upper bound, a corrupt plan falls back to the server settings, and the `platform` tenant always follows the server settings. Kamerplanter creates the plan `standard` at startup, and migration `v0091` records it on every existing tenant.
- **Plans and quotas in the interface** (REQ-056 §15, AK-45): platform admins maintain plans on the new **Plans** page (Settings > Platform Mode > Manage plans): a list with the default mark and the number of tenants, a form to create and change, deleting for unused plans only. An empty quota reads "same as instance setting", a `0` "unlimited" or "budget off". A tenant's page shows plan, usage per quota and the owner and assigns another plan (not for the `platform` tenant). Every member sees their garden's plan and usage in the new **Quotas** tab of the garden settings. The refusals `ORGANIZATION_LIMIT_REACHED`, `MEMBER_LIMIT_REACHED`, `SERVICE_ACCOUNT_LIMIT_REACHED`, `STORAGE_QUOTA_EXCEEDED` and `PHOTO_QUOTA_EXCEEDED` now read as an understandable text in German and English instead of the English server message.

Plant values are only included if you add them to the question yourself — that additionally requires `ai_tenant_data_access`. Revocable at any time, effective from the next question. It is listed under `GET /api/v1/privacy/consents` and granted via `POST /api/v1/privacy/consents`.

New optional consent purpose `pest_reference_contribution` ("Photo contribution to pest recognition"): a pest photo you contributed yourself that an administrator makes visible to everyone is then added to the shared pest recognition index as a numerical fingerprint (embedding) plus provenance; the photo does not leave the installation. Revocable at any time, effective from the next promotion. It is listed under `GET /api/v1/privacy/consents` and in the **Consents** tab; it is granted via `POST /api/v1/privacy/consents` (there is no dedicated switch in the interface yet).

- **Invitation link for several people** (issue #2182, REQ-024 v1.34 AK-07): For an invitation link you set under “People per link” how many people can join with it (1–100, default 1 as before). Every use is counted atomically, the invitation list shows “Used” (e.g. “3 of 20”, as a card on a phone), and every use counts against the member limit. API: `POST /api/v1/tenants/{slug}/invitations/link` accepts `max_uses`, the invitation list carries `max_uses` and `use_count`. If a join fails, the use is handed back — an invitation revoked in the meantime stays revoked. - **OIDC auto-join** (issue #2182, REQ-024 v1.34 AK-09, REQ-023 v1.49): If a sign-in provider has a default tenant (`default_tenant_key`), an account newly created on its first sign-in through that provider joins the tenant as Viewer. Until now the field was stored but had no effect. Never into the `platform` tenant or a personal garden; an unknown, inactive, deleted or full tenant is skipped quietly and the sign-in succeeds. The join is recorded in the security audit log (`via: oidc_auto_join`). Only for a generic OIDC provider (on Google, GitHub and Apple anyone can create an account) and only for an account whose email address the provider reports as verified. Kamerplanter checks the default tenant when it is saved (the tenant exists, is not personal, is not `platform`; otherwise 422), the provider response shows it, and `null` or `""` removes it. If the join fails unexpectedly, the sign-in is not affected.
- **Documentation (issue #2179):** The user guide described a platform role `viewer` with read access to the admin area. That role does not exist; it is now marked “Not yet implemented” (REQ-024 §1a.4).
- **Upgrade from light to full mode** (Issue #1855, REQ-027 v1.9 §7a): Every start records the deployment mode (collection `system_meta`). When a light installation starts with `KAMERPLANTER_MODE=full` for the first time, Kamerplanter locks the light-mode system account (`is_active=false`), revokes its API keys, ends its sessions and deletes its calendar feeds. A `kp_` key minted without sign-in in light mode then gets `401` (AK-35); Home Assistant and MCP clients need a new key. The light-mode garden stays untouched. New: `GET /api/v1/system/takeover-status` and `POST /api/v1/system/takeover` (full mode only): the first registered account — or an existing platform admin — takes the garden over (`accept: true`; it becomes lead with both management scopes, the data stay where they are) or declines; on an instance without a platform admin, either decision makes it the first one. When the instance starts in light mode again, Kamerplanter unlocks the system account and gives it its garden back. Every change is in the security audit (`via: mode_switch` / `light_mode_takeover`, new action `tenant_taken_over`). After the security review: taking over and declining require the account's step-up (new step-up act `light_mode_takeover`); without a platform admin only the first active account registered after the switch with a confirmed address and its own garden decides; the take-over is claimed and removed only after success, a failure midway is undone; full mode never signs the system account in, whatever the database says (MCP included); new audit actions `takeover_accepted`, `takeover_declined`, `takeover_reverted`, `system_account_sealed`; a light start with other accounts writes a `critical` warning. After the second review round: if the take-over fails midway (also while logging or granting the platform admin role), Kamerplanter takes back everything already written; if that fails too, it keeps what is left on the open take-over (`needs_attention`, audit `takeover_undo_failed`) and takes it back before anybody decides again. Refused attempts are in the security audit as `takeover_refused`; only an account that may decide gets a confirmation code. After the third round: the stored remainder no longer contains the deciding account, the undo checks before every step that the decision still holds, a garden deleted meanwhile no longer blocks the take-over for good, an account erasure does not take the light-mode garden along while a remainder exists, and both take-over endpoints are limited to 10 calls per minute and account (`RATE_LIMIT_TAKEOVER`).

### Backend

- **Faster task queue with many gardens** (issue #1534): the task queue, the overdue list and the status-filtered task list of a garden now read only that garden's tasks. Until now each of them read every open task of the whole installation — measured with about one million tasks in 3 400 gardens, roughly 1.4 s per query for a small garden, now about 2 ms. Kamerplanter builds the new database index on the next start (migration `v0092`); nothing changes for you.
- **Fixed (security): the upload limit applies before the body is read, attachments no longer come out of the browser cache unasked** (issue #2254, NFR-013 v1.13). FastAPI reads an upload completely — files above 1 MiB into `/tmp` — before sign-in or the size check run. Measured: a 50 MiB upload against a 1 MiB limit was read to the last byte, without sign-in too. Now the backend checks the size first: every upload is limited to `STORAGE_MAX_FILE_SIZE_MB` + 1 MiB (the same limit as the frontend nginx). With a larger `Content-Length` it answers `413` (`REQUEST_BODY_TOO_LARGE`) without reading a byte; a body without a declared length is cut off at the limit. Concurrent uploads share a budget for `/tmp` (`UPLOAD_SPOOL_BUDGET_MB`, default 52, counted in bytes that arrived); one that gets no room within `UPLOAD_SPOOL_WAIT_SECONDS` (30) receives `503` with `Retry-After`. Downloads via token link (`/api/v1/attachments/token/…`) carry `Cache-Control: no-store` instead of `private, max-age=86400`: the link is valid for 15 minutes, the browser's copy would have lasted a day, even after the attachment was deleted. Attachments and thumbnails in the app carry `private, no-cache` with an `ETag`: the browser asks before every display and gets `304` when nothing changed and you may still see the attachment. Callers that waited for a completed deletion must treat the tenant as frozen. Deletions already running at deploy time are taken over by the daily run after six hours without a heartbeat

Floors: `v0030` (dense index on `harvest_batches.batch_id`, shipped since v0.0.24), `v0041` (global index on `species.scientific_name_normalized`, since v0.2.1), `v0062` (unique index on `attachments.storage_key`), `v0064` (`auth_providers` without the configuration), `v0069` (`fertilizers` across tenants), `v0075` (`tanks.name`), `v0076` (`activities.name`), `v0077` (`workflow_templates.name`), `v0079` (`plant_instances.instance_id`, `harvest_batches.batch_id`, `slots.slot_id`) — the last seven are in no release yet, so no rollback below the next release. Every start of a new image drops such a re-created index again (log event `retired_index_reappeared`); if its replacement is missing it stays, `retired_index_refused_without_replacement` is logged at `error` level and `/api/v1/health/ready` reports `retired_indexes_refused` above 0 (the status stays `ready`). The unique index on `attachments.storage_key` is not dropped again. An old pod that starts *after* the new ones re-creates the index until the next new pod starts. Where two tenants already share a name, the old image does not start at all (`ERR 1210 unique constraint violated`)

Nothing changes for you.

- **Fixed (AI glossary, issue #2169):** After every finished knowledge-base reingest (`ai.knowledge_service_ingest`, Sundays 03:00 UTC) Kamerplanter empties the glossary cache and regenerates the explanations of all curated terms (REQ-035 §4.3). Until now nothing started that chain: the AI explanations expired after their 7 days and were never regenerated, so every term was left showing only its editorial short text. Emptying now also covers the Redis cache, which is read first — otherwise the regeneration would have taken every variant for still valid. Cost: one LLM call per term, language and expertise level per week (currently 32 × 6 = 192); with AI features switched off (`ai_features_enabled`) the regeneration is skipped.

### Deployment (Helm)

- **Fixed (Helm, Docker):** Uploads above 1 MiB failed at the frontend nginx with `413` (issue #2144, audit gap G-10). Neither the image's nginx configuration nor the one the chart mounts over it set `client_max_body_size`; nginx's default of 1 MiB therefore refused every larger attachment, plant and task photo and CSV import, long before the backend's 25 MiB limit (measured in the `nginx-unprivileged` image: 2 MiB and 25 MiB → `413`). Both configurations now accept bodies up to `storage.maxFileSizeMb` + 1 MiB (default `26m`); anything larger — a JSON body too — is refused by nginx with `413`. The chart sets the same limit on the ingress `main` as `nginx.ingress.kubernetes.io/proxy-body-size` (ingress-nginx would otherwise cut at 1 MiB too). **Upgrade note:** `ingress.main` now has defaults in the chart; the Ingress is still only created when you give `hosts`, and `enabled: false` switches it off. The earlier docs recommendation `proxy-body-size: "10m"` was too small for 25 MiB attachments
- **Fixed (API):** A file of exactly the allowed size was refused with `413` before it was read (issue #2144). The `Content-Length` pre-check compared the whole multipart body — file plus boundaries and form fields — with the file limit. It now allows 64 KiB for that envelope (one shared check for attachments, plant and task photos, pest images, reference images and CV diagnosis); the limit for the file itself stays exact, one byte more still gives `413`.
- **Docs / dev chart:** The ingress examples (Helm, ArgoCD, Kubernetes) and `values-dev.yaml` routed `/api` straight to the backend Service. The backend NetworkPolicy admits only the frontend (issue #1159), and only through the frontend nginx do the upload limit and `TRUSTED_PROXY_HOPS: "1"` apply. All examples now send `/` including `/api` to the frontend; in the dev release Vite proxies `/api`.
- **Fixed (Helm):** A rolling update hung on a multi-node cluster when the new backend pod landed on another node than the `ReadWriteOnce` attachments volume (`Multi-Attach error`); a worker on another node than the backend never started (issue #2153). Backend and Celery worker now require the same node via `podAffinity` while the attachments live on a `ReadWriteOnce` volume; the rolling update keeps its zero downtime. With `storage.backend: s3` or `ReadWriteMany` there is no constraint.
- **Fixed (Helm):** The Celery worker has a startup and a readiness probe (issue #2154). Until now it counted as ready at container start, and a rollout replaced the old worker even when the new one could not log in to ArangoDB and failed every task. Now the worker (`WORKER_READY_FILE`, set by the chart) checks its login before the first task, exits after 60 seconds without success and reports ready only once its consumer runs; until then the rollout keeps the old worker. The liveness probe asks only its own worker — until now it succeeded as long as any worker in the cluster answered.
- **Changed (operations):** Celery spreads tasks over three queues (issue #2128, MT-032): `critical` (retention and erasure, privacy sweeps, notifications, frost warning, actuators), `celery` (the default, name unchanged) and `bulk` (dataset and image acquisition, enrichment, glossary warm-up, storage migration). Every task has a time limit as a backstop (30 minutes soft, 35 hard; resumable or deliberately started runs three hours), each worker process reserves one message ahead only, and the Valkey `visibility_timeout` of four hours lies above the longest limit, so a reserved message is not delivered a second time. The chart starts the worker with `-Q critical,celery,bulk`. **Upgrade note:** if you override the worker `args`, carry the queue list over or drop `-Q`; a queue without a reading worker keeps its tasks silently. Rollout order: worker first, then beat and API — an older API keeps sending everything to `celery`, which the new worker reads. Still open from MT-032: the N+1 access in `check_auto_transitions` (not scheduled at present).
- **Added (operations):** One worker per queue (issue #2128, MT-032): with `celeryWorkers.dedicatedQueues: true` the chart runs `celery-worker` for `critical` only plus two copies of it — `celery-worker-default` for `celery`, `celery-worker-bulk` for `bulk` — derived at render time from the merged worker values — overlays on `controllers.celery-worker` and `networkpolicies.celery-worker` (image, environment, `securityContext`, egress) apply to all three, and every policy that admits the worker admits the copies too. The default stays one worker for all three queues; the render without the switch is unchanged. With the default `ReadWriteOnce` volume both copies also run on the backend's node (512 Mi requested each). Idempotent clean-up runs (retention, expired tokens and invitations, audit and cache entries, expired overrides) now acknowledge their message only after the run (`acks_late`), so a vanished worker pod does not lose the run. The care notifications (`notifications.dispatch_due_care`, `notifications.send_daily_summary`) no longer read every task of every tenant into the worker; they ask, per active tenant, for that tenant's open due care reminders in AQL — worker memory no longer depends on the total number of tasks; a tenant whose read fails is logged and skipped, the others still get their reminders. Docs: [Helm — One worker per queue](../deployment/helm.md#celery-worker-pro-queue).
- **Changed (operations):** The beat tasks for actuators, tanks and plants no longer read every tenant's rows into the worker (issue #2128, MT-032). `evaluate_control_rules`, `sync_actuator_states`, `sync_tank_states_from_ha`, `check_tank_alerts` and `evaluate_quarter_climate` first fetch the tenants they may work on and then read only those tenants' rows — tenant, removed plants and a missing Home Assistant entity are part of the AQL query — one page of 1000 rows at a time. The worker holds a page instead of the whole installation, and the rows of suspended or pending-deletion tenants are not read at all. The same applies to the currently unscheduled `check_auto_transitions`, `check_dormancy_triggers` and `update_vernalization_progress`; the last two no longer process plants of inactive tenants either. **Without a tenant (empty `tenant_key`):** in the control loop an actuator without a tenant is now treated like a device of a suspended tenant — a firing safety rule decides, otherwise a device an emergency switches off (a heater, for example) is switched off once; schedules and overrides no longer apply. It used to run like an active tenant's device. Every run with such devices logs `actuator_control_tenantless_devices` with their count. A tank without a tenant is still checked for alerts; the Home Assistant tank and actuator syncs and the plant tasks skip rows without a tenant (Home Assistant read nothing for them anyway). A document that fails validation is skipped and logged with its key (`tenant_walk_skipped_invalid_document`) instead of aborting the run. The `tanks_of_closed_tenants` log counters are gone.
- **Upgrade note (Helm):** The `storage` block of the chart values now takes effect (issue #2124, NFR-013 v1.9). Until now the chart did not read it — `storage.backend: s3` still shipped `local-fs` with a PVC. The chart now derives the `STORAGE_*` variables of the backend and the Celery worker, the `backend-attachments` PVC (only with `local-fs`) and its mounts from it; the S3 credentials come as exactly two keys of the Secret named in `storage.s3.credentialsRef` (default `storage-s3-credentials` with `STORAGE_S3_ACCESS_KEY_ID`/`STORAGE_S3_SECRET_ACCESS_KEY`). Your own `env` entries still override the derived values. **Newly refused:** more than one `backend` or `celery-worker` replica on the default `ReadWriteOnce` volume aborts `helm template`/`helm upgrade`/the ArgoCD sync with a message, because a second pod on another node never starts (`Multi-Attach error`). Ways out: `storage.backend: s3` (mandatory for shared operation), `storage.localFs.pvc.accessMode: ReadWriteMany` with an RWX storage class, or on a cluster with exactly one node `storage.localFs.singleNode: true`. The attachment PVC also carries `argocd.argoproj.io/sync-options: Prune=false,Delete=false` so ArgoCD does not delete it after the switch to S3 — migrate the files first with `python -m scripts.storage.migrate --from local-fs --to s3 --checksum-verify`
- **New (Helm):** ArangoDB backup in the chart (issue #2122, NFR-002 v2.2). With `backup.enabled: true` and `backup.s3.bucket` the chart creates the CronJob `kamerplanter-arangodb-backup`: an `arangodump` of the application database, uploaded with rclone to `s3://<bucket>/<prefix>/<timestamp>/`, `<prefix>/LATEST` as a readable recovery point, server-side encryption and retention (`retentionDays`; the newest dump is never deleted). Off by default — existing installations do not change. The new page "Backup & Restore" describes the restore into an empty namespace; it was run through with a real dump
- **Fixed (Helm):** The backend container starts under a `startupProbe` (issue #2125, NFR-002 v2.3). Until now the liveness probe killed it about 35 s after start — before it ever listened, while migrations and seeds were still running (measured on an empty database: about 40 s to start); a waiting replica never got the intended up to 600 s wait for the migration lock. The new probe gives the start up to 900 s; liveness and readiness only begin after it
- **Security / upgrade note (Helm):** The ArangoDB pod now receives only `ARANGO_ROOT_PASSWORD` instead of the whole `kamerplanter-secrets` (issue #2126, NFR-002 v2.4) — until now `JWT_SECRET_KEY`, `FERNET_KEY`, `INTERNAL_SERVICE_TOKEN` and every mail/API key sat in the database pod. The backend, Celery worker, Celery beat and the backup no longer connect as `root` but with the account `kamerplanter` (`database.arangodb.appUsername`), which a new `app-user` container in the ArangoDB pod creates on every start with `ARANGODB_PASSWORD` — read/write on the application database only, no access to `_system`. The backend can start with such an account now (it used to abort with `401 No read access` because it listed the databases through `_system` first). If your values set `ARANGODB_USERNAME: root` or an `envFrom` on the ArangoDB container (earlier docs examples), root access stays until you remove both; `database.arangodb.appUsername: root` restores the old behaviour explicitly. Recommended follow-ups: a separate `ARANGODB_PASSWORD` and the root password in a Secret of its own (`database.arangodb.rootPasswordSecret`) — see "Database credentials" in the Kubernetes deployment guide
- **New (Helm):** autoscaler, disruption budget and `ExternalSecret` as opt-in (issue #2127, NFR-002 v2.6). `controllers.<name>.horizontalPodAutoscaler` and `controllers.<name>.podDisruptionBudget` add an HPA and a PDB per controller; `externalSecrets.app.enabled: true` lets the External Secrets Operator write `kamerplanter-secrets` from your secret store. Without these settings the chart renders exactly as before. Newly refused: an autoscaler for backend or worker on the `ReadWriteOnce` attachment volume (like several `replicas` already), more than one pod or an autoscaler for `celery-beat`, `arangodb` and `vectordb`, and a PDB that lets no pod be evicted (every node drain would hang) — also with `maxUnavailable: 0` or `"0%"` and with a percentage `minAvailable` that Kubernetes rounds up to every pod. The Helm docs also recommend a memory bound with `noeviction` and AOF for Valkey (not as a default) and record that external databases are not supported yet
- **Docs (Helm):** the backend's start-up time is now documented (issue #2125): up to 900 s to start, up to 600 s waiting for another pod's migration, 300 s until a migration lock counts as orphaned — and how to raise the budget for a very long migration. Migrations and seeds keep running when the backend starts; no separate migration job is needed. A test keeps the table in line with chart and code, and the floor for `failureThreshold` too (70: the 600 s wait plus 100 s of headroom for the pod's own start)
- **Fixed / upgrade note (Helm):** Valkey keeps its queue across a restart (issue #2127, NFR-002 v2.8). The chart set `valkey.dataStorage.size`, a key the Valkey chart does not know — no volume was created, `/data` sat on an ephemeral `emptyDir`, and every restart lost the waiting tasks. Valkey now gets its own volume (`kamerplanter-valkey`, 1 GiB, survives `helm uninstall`), the `Recreate` strategy, `maxmemory 256mb` with `noeviction` (a full memory refuses writes instead of evicting tasks), the append-only file and a 640 MiB memory limit (the render check requires at least twice `maxmemory`). The upgrade restarts Valkey once; tasks waiting at that moment are lost, as with every restart so far — let the queue drain first. Without a default StorageClass Valkey stays `Pending`; then name one in `valkey.dataStorage.className`. For local development `skaffold.yaml` fixes the same key.
- **New (Helm):** TimescaleDB as a chart controller, off by default (issue #2127, NFR-002 v2.8). `controllers.timescaledb.enabled: true` switches on the database, its Service, its NetworkPolicy and `TIMESCALEDB_ENABLED` on backend, worker and beat together. The password comes from the key `TIMESCALEDB_PASSWORD` in `kamerplanter-secrets`, never from the values; the database runs without root privileges on a read-only file system. The commented-out example block with `POSTGRES_PASSWORD: changeme` is gone. The frontend and Valkey init containers now carry resource limits too.
- **New (Helm):** external ArangoDB and external Valkey (issue #2127, NFR-002 v2.9). `database.arangodb.external.enabled: true` switches the bundled ArangoDB off and connects backend, worker, beat and backup to `host`, `port` and `scheme` (`http` or `https`); `valkey.enabled: false` with `database.valkey.external.url` does the same for Valkey. For both the chart renders an egress NetworkPolicy to the given `cidr`. The backend reads the scheme from the new variable `ARANGODB_SCHEME` (default `http`, hard-coded until now) and refuses to start with any other value or with a URL in `ARANGODB_HOST`. Without the switches the chart renders as before, adding only `ARANGODB_SCHEME=http` — the upgrade therefore restarts backend, worker and beat once
- **New (Helm, operations):** worker autoscaling by queue length as opt-in (issue #2128, #2127, NFR-002 v2.10). The backend's metrics port now serves `celery_queue_length` (label `queue`: `critical`, `celery`, `bulk`) and `celery_broker_up` — read at scrape time, at most every 5 seconds; when Valkey is unreachable the queue values are absent and the scrape does not fail. `celeryWorkers.queueAutoscaling.enabled: true` gives each worker a `HorizontalPodAutoscaler` on that series as an external metric, selected by the queues the worker reads. Prerequisites: `monitoring.enabled: true` and a Prometheus Adapter in the cluster that you install yourself — the rule is in the [Helm docs](../deployment/helm.md#worker-autoscaling-nach-queue-laenge). Inconsistent settings (no monitoring, no metric name or target, `minReplicas` not below `maxReplicas`, a second hand-written autoscaler on the same worker) are refused at render time; `minReplicas`/`maxReplicas` and external metrics are now checked on every hand-written autoscaler too. Default: off, existing installations are unchanged.
