- **Privacy: a consent of its own for the AI knowledge question** (REQ-031 v2.6, REQ-025 v1.35). ## Changed

### Documentation

- Light Mode and AI: the specification promised that the backend refuses to start in Light Mode with a cloud language model. That check does not exist, and in the described form it would have had no effect — the Knowledge Service chooses the language model through `LLM_PROVIDER`. The [Light Mode](../user-guide/light-mode.md) page now says that for Light Mode you have to configure a local model on the Knowledge Service (issue #2176).
- Roles and permissions, platform admin: the pages now say what applies — a location assignment does not restrict editing, the first registered account does not become platform administrator automatically (it is set up on the server), a platform administrator sees no plants or harvests of other gardens, and the guided switch from light mode is marked as not built yet.

### Frontend

- **Calendar, iCal feeds (issue #2171):** Kamerplanter shows a feed's subscription URL only once, right after creating the feed or regenerating its token, in a dialog of its own with **Copy URL** and a note that it cannot be retrieved later. The feed list no longer shows a URL or a copy button, but a hint that you regenerate the token to get a new URL. **Regenerate Token** now asks first, because the old URL stops working in every calendar app afterwards.
- **Privacy (behaviour change):** The frontend reports errors only after consent (issue #2159, UI-NFR-013 CI-001/CW-003). Until now the browser started the error-tracking SDK as soon as a `SENTRY_DSN` was set, and the consent banner was mounted nowhere. Now, with a DSN set, the banner appears on the first visit and the SDK is loaded only after consent to error analysis. Under **Privacy → Consents**, "Allow error analysis" turns reporting off or on without a reload, in other tabs too. In Light mode no banner appears and the frontend reports no errors. Without a DSN nothing changes. For operators: frontend errors now arrive only from people who consented.
- **AI Assistant (behaviour change):** In full mode the **AI Assistant** page asks knowledge questions through your garden (`/t/{slug}/ai/knowledge/ask`) instead of the public path, which no longer exists there; Light mode keeps `/public/ai/ask` (issue #2175). If the consent "AI knowledge question to the knowledge base" is missing, the page offers it in place and sends the question again once granted. A garden with AI switched off and a used-up daily quota are explained clearly. If the knowledge base answers with a cloud model, the answer carries the **Cloud processing** label like the other AI answers. The page reads which consent is missing from `details[0].purpose`; only for older servers without that field does it fall back to the message text.
- **Plant recognition (behaviour change):** The **Use as recognition reference** switch is now the consent "Photo contribution to plant recognition" (issue #2174). Switched on, it explains what is shared; on saving, the consent is granted before the photo is contributed. If that fails, the plant is not created and an error is shown instead of silently skipping the contribution. The switch is hidden in Light mode.
- **Privacy:** In the **Consents** tab, every granted optional consent can be withdrawn with **Revoke**; until now that only worked through the API. The "privacy settings" link in the plant-recognition consent dialog now leads to the privacy page instead of the account settings.
- **Glossary:** The **Generate detailed explanation** button disappears once AI features are switched off for the garden or the installation; the reason takes its place instead of a retry button that would be refused the same way.
- **Settings:** Only platform admins see the "Platform Mode" tab; for everyone else the page no longer requests admin data (issue #2144).
- Admin, invitations, the AI assistant, a plant's tasks and storage observations load their lists completely, page by page, now that the API returns at most one page there (issue #2131) — you still see every item.
- Privacy: the account deletion dialog names, before you confirm, the organizations whose management passes to the longest-serving lead or that become orphaned (issue #2134)
- Admin: tenant management shows a tenant's state (active, suspended, deletion scheduled, orphaned, being deleted) with the deletion date and offers **Cancel deletion** with password confirmation while a deletion is scheduled; the active switch and delete are locked meanwhile (issue #2123)
- Logging out — and being signed out because the session was ended elsewhere — now clears everything the browser held for the account: every loaded list, the active garden (`kp_active_tenant_slug`) and this device's browser push registration (issue #2117, MT-020). On a shared device the next person sees none of the previous account's data and receives none of its push messages. A logout whose request fails (offline) still signs the tab out. Light-mode leftovers in the browser (local favorites, module visibility, dashboard layout) are carried into a profile only by the first account that adopts them on this browser.
- Admin: a tenant's page has a **Home Assistant entities** section — the instance's inventory with search, a switch per entity and release by ID for notification services (issue #2112). The sensor and weather-source dialogs request the Home Assistant list only with the **Technical** scope and otherwise explain why it is missing; without releases the sensor dialog points to the platform admin.
- Login and registration follow the registration mode (issue #2132): when registration is closed, the register link is gone and the registration page explains why; when it needs an invitation, the page asks for the **invitation code** (`/register?invitation=<code>` prefills it). A refused sign-in through an OIDC provider explains the reason.
- Invitations: when a garden is full, the invitation acceptance page explains it in your language — and that the invitation stays valid until a seat is free (issue #2133)
- Notifications: Saved Apprise URLs appear masked (`tgram://****#1`); a hint below the field explains how to keep, remove or add them, and Enter now starts a new line (issue #2113).
- Admin: After deleting an organization the interface reports "Deletion accepted" instead of "Organization deleted" — the deletion runs in the background (issue #1792)
- Plant instances are displayed everywhere with a speaking name (e.g. `BASIL-001 (Basil – Genovese)`) instead of only the technical instance ID; the instance ID is preserved as secondary information
- Tasks: the forms in the **Edit** and **Complete** tabs now render validation errors as helper text directly on the affected field instead of a short-lived native browser bubble (`noValidate`)
- Account: the email verification page now offers a **Log in** button in the error case as well (invalid or expired link) — previously that page was a dead end

### Backend

- **Security / upgrade note (API): iCal feed tokens are no longer stored in clear** (issue #2171, REQ-015). Until now every calendar feed's token sat unencrypted in `calendar_feeds.token`, and every read of a feed (`GET /api/v1/t/{slug}/calendar/feeds`, `GET …/feeds/{key}`, `PUT …/feeds/{key}`) returned it together with the subscription URL — anyone able to read the database or a backup could fetch every feed. Kamerplanter now stores only the SHA-256 hash (`token_hash`). The token and `ical_url` appear only in the response of `POST …/calendar/feeds` and `POST …/feeds/{key}/regenerate-token`, i.e. exactly once; every other response carries neither `token` nor `ical_url`. You replace a lost URL by regenerating the token. Migration `v0090` hashes the existing tokens on the first start and removes the clear value: URLs already handed out still resolve their feed. Measured along the way: the public endpoint `GET /api/v1/calendar/feeds/{key}/feed.ics` the subscription URL points at has not been mounted since March 2026 (`404`) — so no calendar app can fetch a feed at the moment; the user guide now says so. **No image rollback below `v0090`:** an older image re-creates the old unique index on `token` and fails to start as soon as two feeds no longer have a clear token. API clients that read `token` or `ical_url` from a read response must switch to the create or regenerate response.
- Security (tenant isolation): the activity catalogue (`GET /api/v1/activities`, `GET /api/v1/activities/{key}`) shows you the global activities and those of your active garden, never another garden's; a foreign key answers "not found". An automatically generated activity plan that every garden shares is now built from global activities only (issue #2119). Today only platform admins create activities and all of them are global — nothing changes for you.
- **BREAKING (API): knowledge questions only inside a garden and behind the AI admission** (issue #2175, REQ-031 v2.5, scenario 15). `POST /api/v1/knowledge/ask` is removed (no alias, `404`). The question to the knowledge base is now `POST /api/v1/t/{slug}/ai/knowledge/ask` — same response body; the request now takes `top_k` ≤ 10 (was 20) and a bounded plant context (`species`, `phase`, `substrate` at most 100 characters each, `ec` 0–20, `ph` 0–14, otherwise `422`). The old route answered any signed-in account, viewers and service accounts included, with a language-model call: no AI toggle, no consent, no daily budget. Like "Why?" and chat, the new route requires the grower role (viewer `403`), the operator switch `AI_FEATURES_ENABLED` (`404`), the garden's AI setting (`403 ai.disabled_for_tenant`), its own consent `ai_knowledge_question` (`403 CONSENT_REQUIRED`; with plant values in `context` also `ai_tenant_data_access`; when the Knowledge Service answers with a cloud model of the platform, also `ai_cloud_processing` and the garden's cloud approval, otherwise `403 ai.disabled_for_tenant` — what counts is the system default provider, not the garden's provider) and the daily AI budget (`429 AI_BUDGET_EXCEEDED`) — all before the Knowledge Service is called. The per-account minute budget `RATE_LIMIT_INFERENCE` stays. When the Knowledge Service cannot be reached it answers `502`. Light mode has no consent; there the knowledge question is `POST /api/v1/public/ai/ask`. `GET /api/v1/knowledge/search` (no language model) is unchanged.
- **BREAKING (API): `/api/v1/public/ai/*` in light mode only** (REQ-031 v2.6 §5.3, REQ-027 v1.8). `POST /api/v1/public/ai/ask` and `GET /api/v1/public/ai/health` were reachable without signing in, in both modes — in full mode the ask route answered any anonymous caller with a language-model call, past consent, the garden's AI switch and the daily budget. In full mode both paths no longer exist (`404`); the knowledge question there is `POST /api/v1/t/{slug}/ai/knowledge/ask`. In light mode they now require a signed-in principal, which light mode supplies as the system user without a login — nothing changes for the light-mode UI. The address limit `AI_PUBLIC_RATE_LIMIT_PER_MIN` and the operator switch `AI_FEATURES_ENABLED` still apply.
- **Privacy (reference image contribution, issue #2174, REQ-034 v1.4 AC-17):** Contributing an identification photo as a reference for the self-hosted recognition (`POST /api/v1/t/{slug}/identification/reference`) now requires the consent "Photo contribution to plant recognition" (`reference_contribution`) — as the automatic contribution from the gallery already did. Without the consent, or after you revoke it, the API answers `403` (`CONSENT_REQUIRED`); your daily quota is not consumed, no contribution is recorded and the image is not processed. The species is resolved only within your tenant: another tenant's private species answers `404` like an unknown one. **Behaviour change:** in Light mode the contribution is no longer possible and answers `409` (`ADAPTER_NOT_AVAILABLE`) — Light mode has no consent management, and REQ-034 switches the reference contribution off there.
- **Privacy (pest recognition, REQ-044 v1.3/v1.4, REQ-010 v1.6/v1.7):** A pest photo that a platform admin promoted to global visibility now enters the recognition index as a reference only if the person who contributed it has given the separate consent "Photo contribution to pest recognition" (`pest_reference_contribution`, REQ-044 v1.4, REQ-010 v1.7). The consent "Photo contribution to plant recognition" (`reference_contribution`) names only gallery photos of plants and does **not** open the pest index; existing grants of it do not carry over — contributors must consent anew. Without the consent, after it is revoked, and always in Light mode, the photo stays promoted and visible, but the background task ends without calling the inference service (`no_consent` or `light_mode`). Revoking does not remove vectors that were already indexed; deleting the photo or the account does.
- **Changed (API): generating a glossary explanation needs the garden's AI approval** (REQ-035 v1.4). `POST /api/v1/t/{slug}/glossary/term/{slug}/generate` now requires the garden-level AI toggle (REQ-031 stage 2) in addition to the role: off → `403` (`AI_DISABLED_FOR_TENANT`) before the cache, the daily quota or the language model is touched. **Behaviour change:** with AI switched off instance-wide the route now answers `404` instead of the curated short definition. Reading (`GET …/glossary/terms`, `GET …/glossary/term/{slug}`, the public and admin routes) is unchanged.
- **Knowledge Service, security (issue #2176):** an unknown `LLM_PROVIDER` value used to fall back silently to the Anthropic adapter — a typo such as `openai-compatible` sent every question, together with the `LLM_API_KEY` meant for the local server, to the cloud. The Knowledge Service now refuses to start with an unknown value and names the allowed ones (`anthropic`, `ollama`, `openai_compatible`).
- **Security (tenant isolation, hygiene bundle, issue #2144):** A set of small gaps from the multi-tenant audit is closed. Every response under `/api/v1/` now carries `Cache-Control: no-store` unless the route sets its own — attachments, pest images and the chat stream keep theirs. "Prepare a substrate batch for reuse" needs at least the Grower role (Viewer: `403`). Changing a member's additional permissions needs the same confirmation as a role change. As a platform admin you can no longer deactivate your own account or the last account holding the platform role (`422`). A comment key that does not belong to the given task answers `404` instead of `422`; the CSV import matches only against species you also see in the species list. A notification without a recipient is no longer stored and readable by nobody. Companion lists, counts and recommendations show only species you may see; companion edges join only global species. Filter field names in database queries are checked before a query is built.
- **Changed (MCP):** An `idempotency_key` sent again with **different** arguments answers `conflict.idempotency_key_reused` (`409` on the REST alias) instead of replaying the first call's result; an expired entry is no longer replayed (issue #2144).
- **New (operations):** `python -m app.migrations.audit_legacy_stamps` lists, read-only, rows whose author is not a member of their garden — traces of the early tenant backfill (v0004). Migration `v0088` removes that stamp from pests, diseases and treatments. Details: `src/backend/app/migrations/README.md` (issue #2144).
- **New (API): service accounts for a garden** (issue #2137, internal reference MT-041). Whoever is a lead **and** holds the Technical scope in a garden creates an account for a machine (Home Assistant, Grafana, CI/CD) with `POST /api/v1/t/{slug}/service-accounts` — without a password, as `viewer` or `grower`, with a first API key that works in this garden only. Also a list, key rotation (`…/{sa_key}/rotate-key`, previous keys revoked at once or after an overlap window of up to 24 h) and removal (`DELETE …/{sa_key}`). Every change asks for your password (step-up `service_account_change`) and is recorded in the security audit log. At most `TENANT_MAX_SERVICE_ACCOUNTS` (default `20`) per garden; a service account takes a seat of the member limit. Light mode: not available. See [Service Accounts & API Keys](../api/service-accounts.md)
- **New (API):** An API key gets an IP allowlist (`ip_allowlist`, CIDR, nothing wider than `/8` or `/32`), a rate limit (`rate_limit_per_minute`, 1–10000) and an expiry (`expires_at`, at most 730 days) when it is issued — for `POST /api/v1/auth/api-keys` as for service accounts. The three values were already enforced, but nothing could set them. An unusable value is a `422` before the password is asked for; the key list shows the values (issue #2137)
- **Changed (API):** A service account can neither found a garden (`POST /api/v1/tenants`) nor accept an invitation (`403`); the member administration does not make it a lead (`403`). Service accounts are now managed by Lead **and** Technical instead of the Management scope (issue #2137)
- Security (tenant isolation): writes to sites, locations, slots and nutrient plans now check tenant ownership in the service itself instead of only in the calling endpoint (issue #2107). Nothing changes for you; a foreign key still answers "not found". Detaching a nutrient plan from a plant and changing or deleting an activity of the shared catalogue are checked in the service too (issue #2120). Migration `v0087` removes the never-populated `tenant_key` field from stored locations and slots.
- **BREAKING (API):** AI calls have a daily budget per account and per garden (issue #2110). Every route that calls a language model — generating tips and the daily tip, "Why?", chat message, generating a glossary explanation, AI diagnosis — counts against `AI_BUDGET_USER_CALLS_PER_DAY` (default `50` per account and garden), `AI_BUDGET_TENANT_CALLS_PER_DAY` (`500` per garden) and `AI_BUDGET_TENANT_TOKENS_PER_DAY` (`2000000` tokens per garden), each per UTC day. Above that the API answers `429` with `AI_BUDGET_EXCEEDED` (`details[0].code` names the budget) and `Retry-After` until the day ends. When Valkey cannot be reached, no AI call runs (`503 AI_BUDGET_UNAVAILABLE`). These routes also carry the per-account minute budget `RATE_LIMIT_INFERENCE`. The AI call log stores each call's token counts (`prompt_tokens`, `completion_tokens`) so a garden's cost is countable. A refused chat message now arrives as an HTTP error instead of a broken stream; the interface explains every refusal.
- **Fixed (API):** A `429` from a limit in the domain code (daily caps of plant identification and reference contribution, API-key limit, AI budget) now carries the `Retry-After` header (issue #2110). With #2109 only the per-minute limit got it; the wait of the others was in the message text only.
- **Glossary:** Whether a generated glossary explanation counts as cloud processing is now decided by the platform's default provider, not by the default of the garden that asked for the term first (issue #2110). The explanation is served to every garden; its cloud notice is now the same for all and stored with the entry.
- **Behaviour change (API):** Six lists that used to return every item now read a bounded window with `offset` (default `0`) and `limit` (default `50`, at most `200`; issue #2131, MT-035): `GET /admin/platform/tenants`, `GET /admin/platform/users`, `GET /tenants/{slug}/invitations`, `GET /t/{slug}/ai/conversations`, `GET /t/{slug}/tasks/plants/{plant_key}` and `GET /t/{slug}/post-harvest/{key}/observations`. The response stays an array; a client without `limit` now receives the first 50 items instead of all and has to read further pages with `offset`. Tenants, users, invitations and conversations are sorted newest first, tasks by due date, observations newest first — on equal timestamps the key decides, so no page returns an item twice or skips one.
- API: `GET /t/{slug}/plant-instances`, `/watering-logs`, `/watering-events` and `/feeding-events` also accept `after=<key>` and page by key instead of by `offset` (issue #2131). These four lists also no longer count every item of the garden on each page — the number was never in the response. A new index `(tenant_key, _key)` on the four collections is built on the next start; measured on ArangoDB 3.12 with 50,000 items of one garden, a page drops from 167 ms (page 1) and 262 ms (last page by cursor) to about 4 ms for plants, and the first page of a small garden from up to 132 ms to about 4 ms for watering and feeding events.
- API: `POST /calculations/sun-times-range` computes at most 366 days per request; a longer range is refused with `422` (issue #2131). Until now one call computed every day between any two dates.
- **Fixed (privacy):** Six clean-up tasks failed with `TypeError` on every run since they were introduced (July 2026) and deleted nothing (issue #2150, NFR-011): `ai.cleanup_expired_conversations`, `ai.cleanup_expired_audit_log`, `glossary.cleanup_expired_cache`, `glossary.invalidate_after_reingest`, `mcp.cleanup_expired_audit_log`, `mcp.cleanup_expired_idempotency`. They now open their database connection through `get_db()` like every other task. After the update the first runs clear the backlog: AI audit entries older than 30 days, expired glossary cache rows and MCP idempotency records older than 24 hours are deleted. Because the idempotency record never went away, an MCP write tool called again with a reused `idempotency_key` returned the stored result instead of running, even after more than 24 hours; with the hourly run the REQ-033 window applies again (24 hours plus at most one hour). AI conversations (90 days) and the MCP audit (90 days) had no entries due yet.
- Privacy: the personal data export (Art. 15/20) now includes your personal garden (issue #2135): sites with GPS coordinates, beds, slots, plants, planting runs, all tasks, the diary and attachment metadata — limited to the personal gardens you own, without other members' account identifiers. From organizations, only the membership and your own contributions remain in the export, as before. Sensor readings and tank, watering and feeding logs are not included yet.
- Privacy: an account deletion no longer leaves an organization without management (issue #2134). If the person was the last one with the management right, the longest-serving lead takes over management (security audit `via: account_erasure`, the members are notified). If no lead is left or the person was the only member, the organization becomes `orphaned` and is deleted after the tenant-deletion grace period; members and platform admins are notified. Until now such an organization stayed forever and could not be administered. The deletion preview (`GET /privacy/erasure-preview`, `GET /admin/platform/users/{key}/erasure-preview`) names both cases in the new `organizations` field. The emergency administration sketched in REQ-023 §5a.5 is dropped.
- **BREAKING (API):** A tenant deletion is now **scheduled** instead of run at once (issue #2123, REQ-024 AK-52). `DELETE /tenants/{slug}` and `DELETE /admin/platform/tenants/{key}` still answer `202`, but with `status: "scheduled"` and `scheduled_for`: the tenant is closed for everybody until then, its members receive an email with the date, and only after `RETENTION_TENANT_ERASURE_GRACE_DAYS` days (default 90, `0` = at once as before) does the daily run delete it. Until then `POST /tenants/{slug}/erasure/cancel` (Lead and Management, password) or `POST /admin/platform/tenants/{key}/erasure/cancel` (platform admin) cancels the deletion. Tenants carry a `status` (`active`, `suspended`, `pending_deletion`, `orphaned`, `deleted`) instead of the `is_active` field for this; migration `v0085` converts existing tenants, and `is_active` stays in the responses as a derived value. A platform admin can no longer reactivate a tenant whose deletion is scheduled through the active switch (`422`) — that is what the cancellation is for.
- **Security (sessions):** Refresh tokens now form a **family** per sign-in (issue #2116, MT-019, REQ-023 §3.2a). Presenting an already rotated refresh token again ends the whole family and is logged as `auth.refresh_replay_detected`; within 60 seconds the same client (same `User-Agent`) on the cookie path receives an access token and no new cookie instead (two tabs renewing at once). The body transport of paired devices has no grace window. Rotated tokens are kept until their own expiry so a late replay is still recognised. **Access tokens end with their session:** they carry the account's token generation (claim `gen`), and every revocation — logout, logout-all, ending one session, a password change or reset, deactivation, an Art. 17 request, the email change and its revert, a detected replay — moves it, so a token issued before is refused with `401` from the next request instead of living out its 15 minutes (REQ-023 AK-14). Ending one session therefore also ends the access tokens of the account's other sessions; those renew silently. No extra database read per request (the account is read anyway). An admin deactivation now ends every session too. Tokens issued before the update stay valid until they expire; no migration, no forced re-login.
- **Security:** Password-reset and email-verification tokens are stored only as SHA-256 digests (`password_reset_token_hash`, `email_verification_token_hash`; issue #2158). Before, the stored value was the link itself, so a read of the database or a backup could take over an account within the reset hour. Migration `v0086` hashes the stored values in place; links mailed before the update keep working once.
- Web push: an endpoint belongs to one account at a time. Subscribing it removes it from every other account (issue #2117) — on a shared device the previous user no longer receives pushes through it.

### Deployment (Helm)

- **Fixed (Helm, Docker):** Uploads above 1 MiB failed at the frontend nginx with `413` (issue #2144, audit gap G-10). Neither the image's nginx configuration nor the one the chart mounts over it set `client_max_body_size`; nginx's default of 1 MiB therefore refused every larger attachment, plant and task photo and CSV import, long before the backend's 25 MiB limit (measured in the `nginx-unprivileged` image: 2 MiB and 25 MiB → `413`). Both configurations now accept bodies up to `storage.maxFileSizeMb` + 1 MiB (default `26m`); anything larger — a JSON body too — is refused by nginx with `413`. The chart sets the same limit on the ingress `main` as `nginx.ingress.kubernetes.io/proxy-body-size` (ingress-nginx would otherwise cut at 1 MiB too). **Upgrade note:** `ingress.main` now has defaults in the chart; the Ingress is still only created when you give `hosts`, and `enabled: false` switches it off. The earlier docs recommendation `proxy-body-size: "10m"` was too small for 25 MiB attachments
- **Fixed (API):** A file of exactly the allowed size was refused with `413` before it was read (issue #2144). The `Content-Length` pre-check compared the whole multipart body — file plus boundaries and form fields — with the file limit. It now allows 64 KiB for that envelope (one shared check for attachments, plant and task photos, pest images, reference images and CV diagnosis); the limit for the file itself stays exact, one byte more still gives `413`.
- **Docs / dev chart:** The ingress examples (Helm, ArgoCD, Kubernetes) and `values-dev.yaml` routed `/api` straight to the backend Service. The backend NetworkPolicy admits only the frontend (issue #1159), and only through the frontend nginx do the upload limit and `TRUSTED_PROXY_HOPS: "1"` apply. All examples now send `/` including `/api` to the frontend; in the dev release Vite proxies `/api`.
- **Fixed (Helm):** A rolling update hung on a multi-node cluster when the new backend pod landed on another node than the `ReadWriteOnce` attachments volume (`Multi-Attach error`); a worker on another node than the backend never started (issue #2153). Backend and Celery worker now require the same node via `podAffinity` while the attachments live on a `ReadWriteOnce` volume; the rolling update keeps its zero downtime. With `storage.backend: s3` or `ReadWriteMany` there is no constraint.
- **Fixed (Helm):** The Celery worker has a startup and a readiness probe (issue #2154). Until now it counted as ready at container start, and a rollout replaced the old worker even when the new one could not log in to ArangoDB and failed every task. Now the worker (`WORKER_READY_FILE`, set by the chart) checks its login before the first task, exits after 60 seconds without success and reports ready only once its consumer runs; until then the rollout keeps the old worker. The liveness probe asks only its own worker — until now it succeeded as long as any worker in the cluster answered.
- **Changed (operations):** Celery spreads tasks over three queues (issue #2128, MT-032): `critical` (retention and erasure, privacy sweeps, notifications, frost warning, actuators), `celery` (the default, name unchanged) and `bulk` (dataset and image acquisition, enrichment, glossary warm-up, storage migration). Every task has a time limit as a backstop (30 minutes soft, 35 hard; resumable or deliberately started runs three hours), each worker process reserves one message ahead only, and the Valkey `visibility_timeout` of four hours lies above the longest limit, so a reserved message is not delivered a second time. The chart starts the worker with `-Q critical,celery,bulk`. **Upgrade note:** if you override the worker `args`, carry the queue list over or drop `-Q`; a queue without a reading worker keeps its tasks silently. Rollout order: worker first, then beat and API — an older API keeps sending everything to `celery`, which the new worker reads. Still open from MT-032: a worker per queue, beat queries per tenant and filtered in AQL.
- **Upgrade note (Helm):** The `storage` block of the chart values now takes effect (issue #2124, NFR-013 v1.9). Until now the chart did not read it — `storage.backend: s3` still shipped `local-fs` with a PVC. The chart now derives the `STORAGE_*` variables of the backend and the Celery worker, the `backend-attachments` PVC (only with `local-fs`) and its mounts from it; the S3 credentials come as exactly two keys of the Secret named in `storage.s3.credentialsRef` (default `storage-s3-credentials` with `STORAGE_S3_ACCESS_KEY_ID`/`STORAGE_S3_SECRET_ACCESS_KEY`). Your own `env` entries still override the derived values. **Newly refused:** more than one `backend` or `celery-worker` replica on the default `ReadWriteOnce` volume aborts `helm template`/`helm upgrade`/the ArgoCD sync with a message, because a second pod on another node never starts (`Multi-Attach error`). Ways out: `storage.backend: s3` (mandatory for shared operation), `storage.localFs.pvc.accessMode: ReadWriteMany` with an RWX storage class, or on a cluster with exactly one node `storage.localFs.singleNode: true`. The attachment PVC also carries `argocd.argoproj.io/sync-options: Prune=false,Delete=false` so ArgoCD does not delete it after the switch to S3 — migrate the files first with `python -m scripts.storage.migrate --from local-fs --to s3 --checksum-verify`
- **New (Helm):** ArangoDB backup in the chart (issue #2122, NFR-002 v2.2). With `backup.enabled: true` and `backup.s3.bucket` the chart creates the CronJob `kamerplanter-arangodb-backup`: an `arangodump` of the application database, uploaded with rclone to `s3://<bucket>/<prefix>/<timestamp>/`, `<prefix>/LATEST` as a readable recovery point, server-side encryption and retention (`retentionDays`; the newest dump is never deleted). Off by default — existing installations do not change. The new page "Backup & Restore" describes the restore into an empty namespace; it was run through with a real dump
- **Fixed (Helm):** The backend container starts under a `startupProbe` (issue #2125, NFR-002 v2.3). Until now the liveness probe killed it about 35 s after start — before it ever listened, while migrations and seeds were still running (measured on an empty database: about 40 s to start); a waiting replica never got the intended up to 600 s wait for the migration lock. The new probe gives the start up to 900 s; liveness and readiness only begin after it
- **Security / upgrade note (Helm):** The ArangoDB pod now receives only `ARANGO_ROOT_PASSWORD` instead of the whole `kamerplanter-secrets` (issue #2126, NFR-002 v2.4) — until now `JWT_SECRET_KEY`, `FERNET_KEY`, `INTERNAL_SERVICE_TOKEN` and every mail/API key sat in the database pod. The backend, Celery worker, Celery beat and the backup no longer connect as `root` but with the account `kamerplanter` (`database.arangodb.appUsername`), which a new `app-user` container in the ArangoDB pod creates on every start with `ARANGODB_PASSWORD` — read/write on the application database only, no access to `_system`. The backend can start with such an account now (it used to abort with `401 No read access` because it listed the databases through `_system` first). If your values set `ARANGODB_USERNAME: root` or an `envFrom` on the ArangoDB container (earlier docs examples), root access stays until you remove both; `database.arangodb.appUsername: root` restores the old behaviour explicitly. Recommended follow-ups: a separate `ARANGODB_PASSWORD` and the root password in a Secret of its own (`database.arangodb.rootPasswordSecret`) — see "Database credentials" in the Kubernetes deployment guide
