## 3. Betroffene Dokumente je Migration

### v0099 — Indizes der Bewässerungszonen (strukturell)

- Legt `irrigation_zones (tenant_key, site_key)` (persistent) und `zone_covers` unique auf `_to` an. Liest und schreibt
  keine Dokumente.
- Der Unique-Index wird nur angelegt, wenn kein Beet zwei `zone_covers`-Kanten hat
  (`ensure_unique_index_when_clean`); sonst **blockiert** (geloggt, im Bericht, Boot läuft weiter, jeder Boot versucht
  es erneut), nie eine Kante gelöscht.
- **Erwartet im Dry-Run:** `duplicate_targets = 0` (vor WP 7.1 schrieb kein Code `zone_covers`).
- Nicht umkehrbar im Sinne von M-6 (der Bootstrap legt die Indizes bei jedem Start an); praktisch harmlos.

### v0100 — `location_key` / `site_key` an Pflanzen nachtragen

- Schreibt `location_key`/`site_key` an `plant_instances`, deren Kette Pflanze → Slot → Location → Site im eigenen
  Mandanten auflöst; überschreibt nie ein gesetztes Feld. Alles andere wird gezählt und nach Grund gelistet
  (`no_slot`, `slot_missing`, `slot_without_location`, `location_missing`, `location_without_site_key`,
  `site_missing`, `site_without_tenant`, `cross_tenant`, `site_mismatch`).
- **Erwartet:** so viele Treffer, wie Pflanzen zwischen WP 3.2 und dem Fix in WP 3.8 über `create_plants` angelegt
  wurden; in Prod unbekannt.
- **Nicht umkehrbar** (abgeleitete Fakten; Zurücksetzen würde die Pflanzen wieder verstecken).

### v0101 — Index der Beetvorlagen und System-Vorlagen

- Index `bed_templates (tenant_key, name)`; legt neun globale Vorlagen mit festem `_key` an, wenn der `_key` fehlt
  (`sys_bed_1x1`, `sys_bed_2x1`, `sys_bed_3x1_2`, `sys_bed_4x1_2`, `sys_raised_bed_1_2x2_4`,
  `sys_raised_bed_2x1x0_8`, `sys_planter_d0_3`, `sys_planter_d0_4`, `sys_planter_d0_5`; Liste `SYSTEM_TEMPLATES`). Vorhandene `_key` bleiben unberührt (eine Betreiber-Änderung wird nie überschrieben).
- **Erwartet im Dry-Run:** alle System-Vorlagen „würden angelegt", wenn Prod v0101 noch nicht hat.
- Rücknahme: die Vorlagen per `_key` löschbar (Plan §8); der Index entsteht beim Start ohnehin neu.

### v0102 — Waisen gelöschter Standorte entfernen, verwaiste Vorlagen-Verweise lösen (destruktiv)

- Entfernt Zeilen in `garden_objects`, `season_states`, `weather_forecasts`, `climate_normals`,
  `weather_source_configs`, `irrigation_demands`, `irrigation_zones`, deren `site_key` auf keinen Standort mehr zeigt;
  Locations und Slots unter verschwundenen Standorten, sofern keine Kante von einem bleibenden Knoten sie erreicht;
  die Kanten dazu. Setzt `template_key` an Locations zurück, deren Vorlage nicht mehr existiert (#2528).
- `care_events` und `garden_plan_audit` sind Historie und werden **nicht** angefasst.
- **Erwartet:** Treffer nur, wenn in Prod vor #2513 Standorte gelöscht wurden. Der Bericht listet je Schritt
  `matched` und die ersten Schlüssel (`details[<step>] = {matched, removed, keys}`).
- **Nicht umkehrbar.** Vor dem echten Lauf ist eine Sicherung der Datenbank Pflicht (§5 Schritt 2).

## 4. Dry-Run ausführen (Betreiber)

Der Dry-Run liest nur und schreibt nichts (M-5). Zwei Wege:

**A — empfohlen: auf einem Abzug.** Prod-ArangoDB sichern (`arangodump`), in eine Dev-Instanz einspielen, dort mit
dem neuen Image:

```bash
cd src/backend
python -m app.migrations current               # welche Version hat der Abzug?
python -m app.migrations upgrade --dry-run     # Bericht aller ausstehenden Migrationen
```

**B — im laufenden Prod-Pod, nur lesend.** Nur mit einem Image, das die neuen Migrationen enthält, **ohne** den
Deployment-Rollout auszulösen (z. B. als einmaliger Job/Pod mit denselben Secrets):

```bash
python -m app.migrations current
python -m app.migrations upgrade --dry-run
```

Achtung: Ein normales `rollout restart` des Backends mit dem neuen Image wendet die Migrationen sofort an — es ist
kein Dry-Run.

**Im Bericht prüfen:**

| Migration | Freigabe, wenn … |
|---|---|
| v0099 | `duplicate_targets = 0`. Sonst: Beete mit zwei Zonen-Kanten klären (der Index bliebe blockiert, die Funktion läuft aber). |
| v0100 | Die Zahl der reparierten Pflanzen ist plausibel; die Gründe der übersprungenen sind verstanden (vor allem `cross_tenant`, `site_mismatch`). |
| v0101 | Nur System-Vorlagen „anzulegen", keine Konflikte. |
| v0102 | Jede `matched`-Zahl ist erklärbar (gelöschte Standorte vor #2513); die gelisteten Schlüssel gehören wirklich zu gelöschten Standorten. **Bei Zweifel nicht ausrollen.** |

## 5. Rollout-Reihenfolge

1. **Vorbedingungen bestätigen:** P-2 (inkl. #2464) und P-4 sind in Prod (B-1). `python -m app.migrations current`
   in Prod notieren.
2. **Sicherung:** vollständiger `arangodump` der Prod-Datenbank, Ablage mit Datum und der in Schritt 1 notierten
   Version. Pflicht wegen v0100/v0102.
3. **Dry-Run** nach §4, Bericht ablegen (Ergebnis in #2493 oder dem Release-Issue verlinken).
4. **Image bauen:** `docker-publish` für `develop` (bzw. den Release-Stand) dispatchen; Memory „Prod-Cluster Deploy-Falle":
   Prod zieht `:latest`, ohne Neustart passiert nichts.
5. **Ausrollen:** `kubectl rollout restart` des Backends (und des Frontends). Beim Start laufen v0099–v0102 unter dem
   Migrations-Lock; danach `python -m app.migrations current` → `0102` und `history` prüfen.
6. **Prüfen nach dem Start:**
   - Backend-Log: `site_orphans_purged` mit den Zahlen aus dem Dry-Run; im Bericht von v0099 kein blockierter Unique-Index.
   - `GET /api/v1/t/{slug}/bed-templates` listet die System-Vorlagen.
   - Ein Standort mit Plan: `GET /sites/{key}/plan` antwortet 200; Zonen anlegen, Gießrunde protokollieren,
     Beet aus Vorlage platzieren, „Neue Saison" im Probelauf — auf einem Testmandanten.
   - Frontend: Ebenen „Zonen", „zuletzt gegossen", „Unterlage" schalten; Bundle lädt (`routeChunks.gardenPlanner`).
7. **Release-Notes:** Welle-7-Funktionen und die bekannten Lücken (by_demand, „Regen — übersprungen",
   `Ctrl/Cmd+D`, Beet räumen ohne Oberfläche).

## 6. Rückfallplan

| Fall | Vorgehen |
|---|---|
| Fehler beim Start **vor** v0100/v0102 (z. B. Image defekt) | Vorheriges Image-Tag ausrollen; v0099/v0101 sind additiv und stören den alten Stand nicht. |
| Fehler **nach** v0100/v0102 | Kein `downgrade` möglich (beide `reversible = False`). Entweder vorwärts reparieren (neues Image) oder den Dump aus Schritt 2 zurückspielen — dann gehen alle Änderungen seit dem Dump verloren. |
| Nur die System-Vorlagen sollen weg | per `_key` löschen (`sys_*`), der Index darf bleiben. Beete, die daraus platziert wurden, verlieren mit #2528 ihren `template_key`. |
| Funktion soll vorerst unsichtbar bleiben | Modul `garden_planner` (REQ-042) für den Mandanten ausblenden; Daten bleiben. |
