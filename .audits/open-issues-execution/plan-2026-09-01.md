## 0. Die zwei Funde, die den Plan verändern

### F-1 — #1334 ist weder „Umbenennung" noch „Endpunkt fehlt" (die dritte Möglichkeit)

Das Issue stellt zwei Optionen zur Wahl: der Client benennt den Pfad falsch, *oder*
ein Batch-Endpunkt war geplant und nie gebaut. **Gemessen ist es keines von beiden.**

Der Server serviert `POST /planting-runs/{key}/transition`. Sein Request-Schema
passt exakt zum Client (`target_phase_key`, `target_phase_name`). Die **Antwort**
passt nicht:

| | Feld |
|---|---|
| Backend `RunTransitionResponse` | `run_key`, `previous_phase`, `new_phase`, `new_phase_name`, `transitioned_at` |
| Frontend `BatchTransitionResponse` | `run_key`, `target_phase`, `transitioned_count`, `skipped_count`, `failed_count`, `transitioned_keys`, `skipped_keys`, `failed_keys` |

Der Dialog liest `result.transitioned_count / skipped_count / failed_count` und
füllt damit drei i18n-Slots. Der Server liefert **keine Zähler** — und zwar
absichtlich. `planting_run_service.py:562`:

> REQ-013 v2.0: The phase lives on the PlantingRun, not on individual
> PlantInstances. **No per-plant exclude is possible.**

Es gibt nichts zu zählen, weil ein Durchlauf **eine** Phase hat. Der Client ist ein
Überbleibsel des Datenmodells **vor** REQ-013 v2.0.

**Folge für die Umsetzung:** Der im Issue naheliegende Fix — Pfad korrigieren, Test
auf den servierten Pfad umstellen — erzeugt einen HTTP 200 und die Meldung
„**undefined** Pflanzen überführt, **undefined** übersprungen". Er sähe grün aus und
wäre falsch. Zum Paket gehören zwingend: Response-Typ ersetzen, Dialog-Text und die
drei i18n-Schlüssel auf eine Aussage über den **Durchlauf** umschreiben.
