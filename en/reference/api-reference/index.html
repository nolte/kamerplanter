    Print & Export (REQ-032)¶

    All print endpoints are located under the tenant-scoped path /api/v1/t/{slug}/print/ and require a valid JWT token. Access rights mirror the permissions of the underlying data (REQ-024 RBAC) — anyone who may read a nutrient plan may also print it.

    Common query parameters (all endpoints):

    Parameter Type Default Values
    locale string de de, en
    format string pdf pdf, csv (tabular templates only)

    Nutrient Plan PDF¶

    Exports a complete nutrient plan as a PDF including the phase table, mixing instructions, water configuration, and CalMag / flushing notes.

    GET /api/v1/t/{slug}/print/nutrient-plan/{plan_key}

    Path parameters:

    Parameter Description
    slug Tenant slug
    plan_key ArangoDB key of the NutrientPlan document

    Response: application/pdf with Content-Disposition: attachment; filename="nutrient-plan-{plan_key}.pdf"

    Example:

    curl -X GET \
  "https://api.example.com/api/v1/t/my-garden/print/nutrient-plan/nutrient_plans/42?locale=en" \
  -H "Authorization: Bearer <token>" \
  --output nutrient-plan.pdf

    Care Checklist PDF¶

    Exports all due care tasks for a given date as a checklist with tick boxes, grouped by urgency (overdue, due today, coming up).

    GET /api/v1/t/{slug}/print/care-checklist

    Query parameters (in addition to locale and format):

    Parameter Type Default Description
    date string (ISO 8601) Today's date Reference date for due tasks, e.g. 2026-04-01

    Response: application/pdf with Content-Disposition: attachment; filename="care-checklist-{date}.pdf"

    Example:

    curl -X GET \
  "https://api.example.com/api/v1/t/my-garden/print/care-checklist?date=2026-04-15&locale=en" \
  -H "Authorization: Bearer <token>" \
  --output care-checklist.pdf

    Plant Info Cards / Label PDF¶

    Prints compact info cards with a QR code for one or more plant instances. The QR code contains the deep-link URL to the respective plant in the app.

    GET /api/v1/t/{slug}/print/plant-labels

    Query parameters (in addition to locale):

    Parameter Type Required Default Description
    plant_keys string Yes — Comma-separated ArangoDB keys of the plant instances (at least 1)
    fields string No name,scientific_name,planted_date Comma-separated fields to show on the card
    layout string No grid_2x4 single (A6), grid_2x4 (8 per A4), grid_3x3 (9 per A4)
    qr_size_mm integer No 25 QR code side length in mm (min: 20, max: 60)

    Possible values for fields:

    name, scientific_name, family, planted_date, current_phase, location, cultivar, note

    The QR code is always included and cannot be deselected via fields.

    Response: application/pdf with Content-Disposition: attachment; filename="plant-labels.pdf"

    Example — 8 cards per A4 page with plant name, scientific name and planting date:

    curl -X GET \
  "https://api.example.com/api/v1/t/my-garden/print/plant-labels\
?plant_keys=plant_instances/101,plant_instances/102,plant_instances/103\
&fields=name,scientific_name,planted_date,location\
&layout=grid_2x4\
&qr_size_mm=25\
&locale=en" \
  -H "Authorization: Bearer <token>" \
  --output labels.pdf

    Error codes:

    HTTP status Meaning
    400 Invalid parameters (e.g. unknown layout value, qr_size_mm out of range)
    401 Not authenticated
    403 No permission for this tenant or resource
    404 Plan key or plant instance key not found
    422 Required parameter missing (e.g. plant_keys for /plant-labels)

    Bed history and care log (REQ-053)¶

    Read endpoints of the bed history. All need a valid JWT and are open to every member of the tenant; a bed or entry of another tenant answers like a missing one with 404.

    GET    /api/v1/t/{slug}/locations/{key}/history                       # care entries + planting events
GET    /api/v1/t/{slug}/locations/{key}/rotation                      # timeline per year (family, nutrient demand, role)
GET    /api/v1/t/{slug}/locations/{key}/succession-recommendation     # next crop: the next step of the rotation
GET    /api/v1/t/{slug}/sites/{key}/rotation-matrix                   # crop rotation matrix: beds × years of a site
GET    /api/v1/t/{slug}/locations/{key}/soil-analyses                 # soil analyses as series per method
GET    /api/v1/t/{slug}/locations/{key}/companion-edges               # companion layer: judged neighbouring pairs
GET    /api/v1/t/{slug}/locations/{key}/summary                       # bed head incl. the nutrient hint
POST   /api/v1/t/{slug}/locations/{key}/history/backfill              # fill in an earlier year (grower and above)
DELETE /api/v1/t/{slug}/locations/{key}/history/backfill/{event_key}  # take a backfilled year back
GET    /api/v1/t/{slug}/care-events                                   # care log of the whole tenant

    GET …/history returns the stored care entries of the bed and the planting events derived from plants and runs in one list, newest first. Every item carries kind (care_event, plant_planted, plant_removed, run_started, run_completed), at and category (planting or removal for planting events). For care_event the whole entry is in care_event. Here as in GET /care-events, a care entry lists the readable names of its plants in plant_names (plant_name, else instance_id, in the order of plant_keys; a deleted plant is missing), so the list needs no request per row. summary stays the stored text; the app words a position correction itself, with the plant's name.

    Parameter Default Description
    category – Only this category (422 for an unknown one)
    plant_key – Only entries that name this plant (runs drop out)
    from, to – Period, inclusive; to before from is 422. An instant without a time zone is read as UTC
    performed_by – Account key of a member. Role viewer/grower: only your own account (403 otherwise); lead and the management scope: any member. The _anonymized marker cannot be filtered (422). Planting events have no performer and drop out
    include_corrections false Also replaced entries and position_corrected
    offset, limit 0, 50 Page; limit at most 200

    GET …/soil-analyses returns the measurements of the bed's soil_analysis care entries as series per parameter and method (ec by ec_method, ph by ph_method, the rest by extraction_method; unknown is its own method). A change of method is listed in method_changes. Values of different methods are never merged, compared or converted. Filters: parameter, from, to; limit (1 to 500, default 200) bounds the number of analyses, truncated says whether older ones were left out. A content class (content_class, A to E) appears only when a lab stated it by the CAL method; it is never computed. When a soil_analysis is created, the server writes the newest values (ph, ec_ms_cm, humus_percent, caco3_percent, each with its method, and last_analysis_at) into the soil profile in the same transaction, but only if the analysis is newer than last_analysis_at; values in a unit other than the profile's own (pH, mS/cm = dS/m, %) are not taken over and never converted. A conductivity needs its ec_method (422 without). liming_hint (status = likely, not_indicated or not_assessable, plus reason) is the "liming likely worthwhile" hint of the current soil profile: likely only with growing_medium_kind = native_soil, a known soil_texture, ph_method = cacl2 and ph below the stated target_ph; otherwise reason names the first missing precondition (no_ph, not_native_soil, ph_method_not_cacl2, texture_unknown, no_target_ph). There is no lime amount.

    GET …/summary returns the head of the bed view (area, status, counters, last care). For a bed (is_bed = true) it carries nutrient_hint, otherwise null: state (ok, check, likely_deficit or insufficient_data), confidence (low, medium, high), reasons[] (reason codes, deciding ones first, for example thresholds_without_source, feeding_overdue, k_class_low, preceding_nitrogen_fixer, standing_nitrogen_fixer, bark_mulch_n_binding, p_or_k_class_high, species_not_readable, check_salt_content), compost_and_p_withheld, withheld_source and sources[]. The hint never contains a number or a fertiliser amount. Every threshold takes part only with a value and a source; none ships with one, so every bed answers insufficient_data with thresholds_without_source. The one rule active as shipped: when a lab result (CAL) puts P or K into class D/E, compost_and_p_withheld is true (compost then serves no nutrient supply, it stays possible as a soil improver) and withheld_source names the source (R-006). A feeding and a soil_amendment with manure or horn shavings count as N input, compost does not. check_salt_content ("check salt content") appears when the soil conductivity (ec_ms_cm) lies above a configured, sourced salt limit and was measured with the same ec_method the limit holds for (no conversion between methods, not for a mineral substrate). The code changes neither state nor an amount. No limit ships, so the code only appears once somebody configures a value with a source. Readable by every member.

    GET …/companion-edges returns the companion layer of the bed: one judged line per neighbouring pair of plant places (adjacent_to) in which both places hold a species. A species counts when a plant stands there or a live planting run plans it there, the same set as POST …/validate-planting. status is compatible, incompatible or unknown and follows the same rule as the planting dialog: an incompatibility wins, else a compatibility with its score, else the relation is unknown. With several species on one place the strongest statement wins. reason_code (companion.incompatible, companion.compatible, companion.unknown) is the key for display, reason the stored reason of an incompatibility, deciding names the two deciding species. slot_a and slot_b carry slot_key, species_keys and position ({x, y} in plan coordinates in metres, null without geometry). The work is bounded: at most 2000 pairs (the first by place keys) and at most 8 species per place are judged (species_truncated is true when a place holds more). Of the judged pairs at most 500 are returned, incompatible first, then compatible, then unknown, each by place keys. total counts all pairs exactly, truncated is true when pairs are missing. When a bed has more than 2000 occupied pairs, the pairs beyond that window are not judged, whatever their status would be.

    GET …/rotation returns for each year the families that stood in the bed (family_key, family_name, nutrient_demand, plan_role, source = plant or backfill). years defaults to max(rotation pause of the families involved, 5), at most 10 (422 above).

    GET /sites/{key}/rotation-matrix puts these timelines of all beds of a site side by side: columns are the years, and for each bed cells holds, per year, the same list as GET …/rotation of that bed (family, nutrient_demand, plan_role, season). years as above (1 to 10); the default is read from the beds of the page, so send the years of the first answer when you page on. Beds are listed by name, at most 500, paged with offset/limit (limit at most 200); total is the number of beds read (after the cap of 500, the basis for paging), truncated is true when the site holds more than 500 beds and the rest is left out. A bed without the rotation check is listed with rotation_applicable: false and the reason in not_applicable_reason; years before rotation_reset_at are left out. Two future years follow the current one: there, and in the current year, the planting runs still planned at the bed stand with source: planned (by their window planned_from/planned_until), but never in a year in which something already stood in the same season. GET …/rotation shows no plans. Readable by every member; the budget is RATE_LIMIT_PLAN_EXPORT per account.

    POST …/locations/{key}/validate-planting when replanting. The call optionally takes replant_of_plant_key, the key of the plant being replaced. That plant then no longer counts as "family stood here this year", and a residual finding depends on its cause of loss: rotation.replant_after_biotic_failure (warning) for disease or pests, rotation.replant_cause_unknown (info) for an unknown or missing cause, nothing for frost, heat, drought, waterlogging, neglect or mechanical damage. Items in rotation[] carry termination_cause. A key that is unknown, belongs to another bed or tenant, or to a plant that did not die this year is ignored without an error; after a recorded soil change (rotation_reset_at) the finding is dropped.

    GET …/succession-recommendation suggests families and species for the next year, the order only, never an amount. The step after the latest recorded year follows the cycle heavy feeder → medium feeder → light feeder → green manure or fallow → heavy feeder (target); candidates are the successors stored in the crop rotation data for that year's families (families[] with species, at most 20), minus the families whose rotation pause in this bed is not over (held_back[]). A species appears only when its nutrient demand is stored; there is no default. status explains an empty list: no_history, demand_unknown, no_successor_data, no_matching_species or not_applicable (rotation check off, reason in not_applicable_reason). previous names the year the recommendation is based on. Readable by every member.

    POST …/history/backfill takes {year, season?, species_key?, family_key?, plan_role}. year lies between the current year minus 10 and minus 1 (422 backfill.year_out_of_range). A species names its family; a differing family_key is 422 backfill.family_mismatch. Only a fallow year (plan_role: fallow) needs no family. The server writes the care entry itself; a client cannot set the trigger.

    GET /care-events is the care log of the whole tenant with the same filters plus location_key and include_superseded. Without a period, bed or plant filter it shows the last 90 days.

    GET /care-events?format=csv returns the same entries (same filters, same role rules) as a file instead of one page of JSON: UTF-8 with BOM, RFC 4180 quoting, a display name instead of an account key. Cells that start with =, +, -, @, a tab or a carriage return get a leading ' so a spreadsheet does not run them as a formula. delimiter=semicolon is the Excel variant for locales with a decimal comma. offset and limit do not apply; more than 50,000 rows is 422 export.too_many_rows (narrow it by bed, plant, category or period). The budget is RATE_LIMIT_CARE_EVENTS_EXPORT per account; the JSON list does not count against it.

    GET /api/v1/t/{slug}/locations?site_key=…&format=csv returns the bed list of a site as a file instead of JSON (beds only, sorted by name; is_bed=false is 422 export.beds_only; UTF-8 with BOM, cells that start with a formula character are neutralised as for the care log). As in the care-log CSV, the header row holds the column ids (name, area_m2, assigned_to …) and enum cells hold the API's values (active, loam, full_sun …); only type and irrigation zone appear with their names. columns is a comma-separated selection (default: name,type,area_m2,status,soil_texture,irrigation_zone,active_plants; the site conditions are selectable on top); an unknown name is 422 export.unknown_column, an empty selection 422 export.no_columns. include_assignment=true (default false) appends the column assigned_to with the display names of the assigned members. delimiter=semicolon is the Excel variant (semicolon, decimal comma), locale=de|en sets the language of the type names. More than 2,000 beds is 422 export.too_many_rows. The budgets of the garden-plan exports apply, RATE_LIMIT_PLAN_EXPORT per account and RATE_LIMIT_PLAN_EXPORT_TENANT per tenant, both to format=csv only; the JSON list does not count against them.

    Bed photos (REQ-053)¶

    Photos of a bed with a cover photo. A photo is a file of category location that you upload beforehand with POST /api/v1/t/{slug}/attachments (category=location); EXIF and GPS data are removed on upload. A bed or photo of another tenant answers like an absent one with 404.

    GET    /api/v1/t/{slug}/locations/{key}/photos                   # the bed's photos, newest first (every member)
POST   /api/v1/t/{slug}/locations/{key}/photos                   # link a photo (role grower and up)
PUT    /api/v1/t/{slug}/locations/{key}/photos/cover             # choose the cover, or clear it with null (grower and up)
DELETE /api/v1/t/{slug}/locations/{key}/photos/{attachment_id}   # remove a photo (own from grower, another member's lead only)

    All four answer with {location_key, cover_photo_ref, photos[], max_photos}.     Accept or dismiss suggested tasks (REQ-053)¶

    A suggested task is an open task with suggested = true; suggestion_reason gives the reason. Both endpoints need the role grower or higher (viewer → 403), write nothing but the task itself and answer with the changed task (TaskResponse).

    POST /api/v1/t/{slug}/tasks/{key}/accept-suggestion    # becomes an ordinary open task
POST /api/v1/t/{slug}/tasks/{key}/dismiss-suggestion   # closes the suggestion as skipped

    accept-suggestion sets suggested = false and clears suggestion_reason; status, due date and everything else stay. Who made the suggestion stays in origin and source.

    dismiss-suggestion takes the optional body {"reason": "…"} (at most 500 characters, other fields → 422) and sets status = skipped, completed_at to the moment it was closed and completion_notes to the reason. suggested stays true: the suggestion was never accepted, and every view that hides suggestions keeps hiding it. No care entry and no notification are written, and the task does not count as done. POST …/tasks/{key}/reopen brings a dismissed suggestion back.

    The check and the write are one statement: if two people decide at the same time, one wins and the other gets 409.

    HTTP status Code Meaning
    403 FORBIDDEN Role viewer
    404 ENTITY_NOT_FOUND Task not found (or not in this tenant)
    409 task.not_a_suggestion The task is not (or no longer) a suggestion, for example because it was already accepted
    409 task.suggestion_closed Dismiss only: the suggestion is already closed (completed, skipped or dismissed)
    409 WRITE_CONFLICT A concurrent write on the same task; try again

    Buffered writes: client_event_id¶

    A client that queues writes while offline sends each one with its own client_event_id (a UUID) so a retry never creates a second object. Five routes take it: POST /care-events and POST /tasks/{key}/complete in the body, POST /tasks/batch/status once for the whole batch (each task gets its own id derived from it), and the photo uploads POST /attachments and POST /plant-instances/{key}/photos as a form field. The id is unique per tenant.

    The first request answers as before (201 for a new care entry). Sending the same id again answers 200 with the object the first request created and writes nothing; a completed task stays completed even if it was reopened in between. Two requests with the same id at the same moment create exactly one object. A care entry shows its client_event_id only to the member who wrote it. If you deleted what a request created (a photo, a task), a later retry with the same id creates nothing and answers 404 client_event.deleted; drop the queued entry.

    HTTP status Code Meaning
    409 client_event.payload_mismatch The id was already used for a different request (another task, plant, file, category or member)
    409 task.already_closed The task is already completed or skipped (before: 422 VALIDATION_ERROR)
    404 task.missing The task was deleted or is not in this tenant (before: 404 ENTITY_NOT_FOUND)
    404 client_event.deleted What this id created was deleted since; nothing was written

    In a batch, a task that is already closed is listed under failed with its code, as is a task this batch completed that was deleted since (client_event.deleted, never a 404 for the whole batch); a replayed task is listed under succeeded.

    Not implemented yet: generating suggestions

    Kamerplanter itself does not create tasks with suggested = true yet. The endpoints are ready, but in a running installation they only have something to decide once a later version creates suggestions.

    Create a mixed culture in one step (REQ-053)¶

    POST /api/v1/t/{slug}/planting-runs/mixed-culture creates one run per species of a mixed culture on the same bed, all in one step (role grower or higher). Each item of runs[] carries in entry.row_assignment the rows (counted from 0) its species takes. Every row belongs to exactly one species: when the rows of two items overlap, the API answers 422 before anything is stored. Only items with a row layout (grid, rows, triangular) and a row_assignment take part; an area (zone), free positions (free) and items without a layout take no rows. The error names the pairs in details[0].conflicts as {"runs": [i, j], "rows": [...], "rows_total": n} (positions in runs[], the shared rows in ascending order and their count), at most 20 pairs with at most 50 rows each; details[0].pairs_total gives the number of all pairs, and details[0].truncated is true when anything was cut. details[0].field points at the later item of the first pair.

    Limit of the check

    The row index refers to the row grid of its own item (row_spacing_cm, row_direction, edge margins). When two items use different grids, their plants can stand at the same spot although the index sets are disjoint. The planting dialog lays all species out on one shared grid; when you call the API directly, send the same row settings for every item.

    Error codes:

    HTTP status Code Meaning
    403 FORBIDDEN Role viewer
    404 ENTITY_NOT_FOUND Bed not found (or not in this tenant)
    422 layout.row_assignment_overlap Two items with a row layout claim the same row index (assuming the same grid, see above)
    422 layout.spacing_required, layout.too_many_positions, plan.quota_exceeded The layout of one species cannot be computed or exceeds a limit
    422 VALIDATION_ERROR with reference.not_found A species or cultivar does not exist or belongs to another tenant

    Switch the crop rotation check per bed (REQ-053)¶

    PATCH /api/v1/t/{slug}/locations/{key} (role grower or higher) takes two fields for the crop rotation check that POST …/locations/{key}/validate-planting and GET …/locations/{key}/rotation evaluate:

    Field Values Meaning
    rotation_enabled true, false, null true switches the check on for this bed, also for pots (planter), tents (tent) and shelves (shelf), where it is otherwise off. false switches it off. null (default) follows the location type
    rotation_exempt true, false Permanent crop (asparagus, berry shrubs): the check is off whatever rotation_enabled says. null is not allowed

    When the check is off, both routes answer rotation_applicable: false with the reason in not_applicable_reason: rotation.not_applicable.rotation_exempt, rotation.not_applicable.disabled (switched off for the bed) or rotation.not_applicable.container (pot, tent, shelf without a switch). Both fields are also part of the garden plan's JSON backup; an older file without them gives a bed that is not exempt and follows its location type. In the file both must be JSON booleans ("yes" or 1 gives validation.invalid), and the import refuses a bed with both set to true with import.rotation_exempt_and_enabled.

    The switch also governs the check per plant place: when the check is off for a bed, POST …/plant-instances with a slot_key and POST …/planting-runs/{key}/create-plants no longer refuse a planting in that bed with ROTATION_VIOLATION, and POST …/plant-instances/slots/{slot_key}/validate-planting reports it as valid.

    One planting position, one plant. POST …/plant-instances with the slot_key of a slot with the role position refuses a second plant with 409: slot.occupied when a plant of the tenant stands there already (removed_on empty), and slot.already_planned with conflicting_run_key, overlap_from and overlap_until when a planned or running planting run reserves the spot for a window that has not ended. Both are in details[0] with field: "slot_key". Rows and areas (row, zone) keep taking several plants. The check reads before it writes; two simultaneous requests for the same spot can both pass it, as when the plants of a planting run are created.

    Error codes:

    HTTP status Code Meaning
    403 FORBIDDEN Role viewer
    404 ENTITY_NOT_FOUND Bed not found (or not in this tenant)
    422 patch.rotation_exempt_and_enabled After the change both rotation_exempt and rotation_enabled would be true; to exempt a switched-on bed, send rotation_enabled: null with it
    422 VALIDATION_ERROR rotation_exempt: null or a value that is not a boolean

    Sun and reach thresholds of a site (REQ-053)¶

    POST /api/v1/t/{slug}/sites and PUT /api/v1/t/{slug}/sites/{key} take two optional objects that set where the sun classes begin and how wide a bed may be before the hint "hard to reach" (bed.reach_too_wide) appears. GET always returns the effective values: the stored ones, else the defaults. Left out or null means "keep the stored value" on an edit.

    Field Default Meaning
    sun_class_thresholds.full_sun_min_hours 6 Full sun above this many hours of direct sun on the reference day
    sun_class_thresholds.partial_shade_min_hours 3 Lower bound of partial shade
    sun_class_thresholds.shade_min_hours 2 Lower bound of shade; below it deep shade
    sun_class_thresholds.reference_month, reference_day 6, 21 Reference day (21 June)
    reach_thresholds.both_sides_m 1.2 Widest bed with access from two opposite sides
    reach_thresholds.one_side_m 0.6 Widest bed with access from one side or unknown access

    The hour bounds must be above 0 and strictly descending, and one_side_m may not exceed both_sides_m; otherwise 422. The hint reads a bed's access only from its access sides (site_conditions.access_sides), not from adjacent paths.

    Reading the Garden Plan: Areas (REQ-053)¶

    GET /api/v1/t/{slug}/sites/{key}/plan returns the whole plan of a site. Two fields tell which locations are areas (a garden, terrace, balcony, greenhouse or room) and which are beds:

    Field Meaning
    area_type_keys Every location type the plan draws as an area, sorted, also those no location of this plan has yet. A type is an area type when it is neither a bed (is_bed) nor carries a planting grid (supports_layout); tent and shelf therefore do not count.
    locations[].is_area true for an area. For every other location the field is absent. For an area, bed_status has no meaning.
    bed_type_keys Every location type flagged is_bed, sorted. A client checks the rule "two beds of one parent location do not overlap" (bed.overlap) with it before the save; the server still checks it.
    locations[].parcel_label The bed's fixed parcel number (one line, at most 40 characters). Absent when none is set.

    A bed lying completely inside an area names it in parent_location_key only when it was created inside the area after the area; there is no endpoint to move existing beds into an area. Both fields are additions; older clients read the response unchanged.

    Writing the parcel number. You set parcel_label with PATCH /api/v1/t/{slug}/locations/{key} or with update_fields in the plan batch; null or a blank text removes it, surrounding space is stripped. More than 40 characters, a line break, a control or bidi character give 422. PUT /locations/{key} leaves the value unchanged. The bed list CSV has the selectable column parcel_label, and the JSON backup carries the field.

    Caching. GET …/sites, GET …/sites/{key}/plan and GET …/locations/{key}/summary answer with Cache-Control: private, no-cache: the browser may keep them for the offline view but must ask the server before every reuse. Every other answer under /api/v1/ carries Cache-Control: no-store, an error answer of these three included. The app fetches the three paths with the request cache mode no-store, so only its own offline store, separated per account and garden, keeps them and not the general browser cache; POST /auth/logout and /auth/logout-all also answer with Clear-Site-Data: "cache". Your own clients should fetch the three paths the same way.

    Three exports of one site's garden plan (REQ-053). All three need a valid JWT and are open to every member of the tenant. A site of another tenant answers 404, like an absent one. Each route allows RATE_LIMIT_PLAN_EXPORT requests per account (default 10 a minute) and RATE_LIMIT_PLAN_EXPORT_TENANT per tenant (default 30 a minute); above that the API answers 429 with Retry-After.

    Garden Plan save: geometry errors¶

    PUT /api/v1/t/{slug}/sites/{key}/plan/boundary (the boundary) and POST …/plan/batch (a batch of operations) refuse a shape that breaks a geometry rule with 422 VALIDATION_ERROR (REQ-053). On the boundary route, a vertex or origin outside the plan's coordinate range (0 to 1000 m) carries code: "geometry.invalid"; for a polygon or polyline vertex the entry also carries point_index, the position of the first such vertex in points (counted from 0). The other shape rules there (dimensions, vertex count, rotation) answer with the generic code: "value_error". In a batch, every geometry defect carries code: "geometry.invalid" with op_index naming the operation and, for a vertex, point_index. Slots and bed templates are saved on their own endpoints in the bed's frame (−1000 to 1000 m) and report an out-of-range vertex the same way.

    Earlier states of the plan (snapshots)¶

    A replace import writes the plan it overwrites to the change log as an import_snapshot (kept as long as the log, one year; a site keeps at most its 20 newest snapshots, and a replace or restore that writes a 21st removes the oldest). Both routes are lead only; a site of another tenant answers 404, and so does a snapshot of another site or tenant.

    GET  /api/v1/t/{slug}/sites/{key}/plan/snapshots                        # list, newest first, paged (limit/offset)
POST /api/v1/t/{slug}/sites/{key}/plan/snapshots/{audit_key}/restore    # { "dry_run": true, "force": false, "confirm_site_name": null }

    The list names, per snapshot, audit_key, revision, at, summary, changed_by_name and the number of locations, garden objects, slots and zones, never the plan itself. The restore is a replace with the stored plan (same checks and same report as the import; confirm_site_name is required unless dry_run); the plan it overwrites is saved as a snapshot of its own first. Zones of the site that the snapshot does not name are retired. 409 import.not_empty while a bed holds an active plant (force lifts that). A merge import creates no snapshot.

    Thinning a zone: zone stand (REQ-053)¶

    GET /slots/{key}/thinning returns the thinning plan of a sown slot. max_count is the most single plants one operation creates (500). For a zone, max_stand_count also names the most plants that may be recorded as a stand (100,000); for a row it is null.

    POST /slots/{key}/thinning thins the slot. Up to max_count, single plants are created as before. If the number for a zone is higher, no plants are created and the answer carries stand_quantity with the recorded number (otherwise null). The stand is added to the run's actual_quantity, the care entry has no plant_keys (whole bed), and the slot keeps sown_at and gets thinned_at. A row above 500 and a zone above max_stand_count still answer 422 plan.quota_exceeded. Sowing or thinning a slot that holds a stand answers 409 slot.occupied; clearing the bed ends the stand.

    Response New field Meaning
    Slot (GET /slots/{key}) and planting (GET /locations/{key}/plantings) thinned_at Day a zone was thinned into a stand, otherwise null
    Plant state (GET /locations/{key}/plant-states) kind = "stand", sown_on planted_on is the thinning day, sown_on the sowing day, lifecycle active, plant_key is null

    Irrigation zones, watering round and zone quota (REQ-053)¶

    Irrigation zones belong to a site. Every member may read; creating, changing and assigning beds needs "grower" or above; only the lead may delete. A zone or site of another tenant answers like a missing one with 404.

    GET|POST         /api/v1/t/{slug}/sites/{key}/irrigation-zones         # list, paged (limit/offset) | create
GET|PATCH|DELETE /api/v1/t/{slug}/irrigation-zones/{key}
PUT              /api/v1/t/{slug}/irrigation-zones/{key}/locations     # { "location_keys": [...] } replaces the beds
GET              /api/v1/t/{slug}/irrigation-zones/{key}/status        # last watering, next, demand, consumption, hints
POST             /api/v1/t/{slug}/irrigation-zones/{key}/log-watering  # watering round

    Assigning beds: A bed belongs to at most one zone. If it already lies in another zone of the same site, PUT …/locations moves it without asking; the response says so in moved_from. A bed outside the site is 422 reference.not_found with its position.

    Watering round: body { "volume_liters": 60, "allocation": "by_area", "performed_at": null, "summary": "Morning round" }. volume_liters more than 0 and at most 100,000; allocation is by_area (by the beds' area_m2) or equal; summary at most 500 characters. Every bed gets one watering entry, all in one transaction, each marked with its allocation: the amount is divided, not measured. Each account may log RATE_LIMIT_ZONE_LOG_WATERING rounds (default 20 per minute). There is no by_demand distribution and no "rain - skipped" round.

A zone in the file has no stable identity: importing the same file twice with merge creates its zones twice.     HTTP status Code Meaning

    When several sensors measure the same quantity, values shows the freshest reading.     Existing integrations reading values keep working unchanged — the map keeps its key and its field names. It is explicitly a summary, though: as long as sensor_count is greater than 1 there is more to see, and readings shows it.

    Plant Instances: Pup Ancestry (mother_key)¶

    When a monocarpic mother plant automatically transitions into its final flowering phase, Kamerplanter automatically creates a new plant instance (the pup) and links it to the mother plant.

    Additional Field in the Plant Instance Response¶

    GET /api/v1/t/{tenant_slug}/plant-instances/{key}

    PlantResponse now additionally includes:

    Field Type Meaning
    mother_key string | null Key of the mother plant this instance descended from as a pup. null for directly created plants.

    The authoritative ancestry relationship is additionally stored as a descended_from graph edge (pup → mother); mother_key mirrors it for cheap frontend access without requiring a graph-traversal query.

    Trigger and Behaviour¶

    • The automatic pup spawn is triggered as soon as a plant species configured as monocarpic (flowering_strategy: "monocarpic") automatically transitions into one of its terminal reproductive phases (flowering, fruiting, or ripening).
    • Exactly one new plant instance is created; re-evaluating the same transition does not create a second pup (idempotent — guarded by the existence of an inbound descended_from edge on the mother).
    • The pup inherits tenant_key, species_key, cultivar_key, and the mother's location, but no slot (slot_key: null) — the mother plant keeps its slot while it senesces. Its planted_on is set to the transition date.
    • In addition to the edge, a PropagationEvent with method: "clone" is persisted (mother → pup).

    No dedicated endpoint, no manual trigger

    The pup spawn is a side effect of the automatic phase transition (see Growth Phases — Automatic Phase Transitions) and has no dedicated REST endpoint for manual triggering or for querying propagation history. The full propagation API (ancestry traversal, listing propagation events per plant) remains REQ-017 follow-up work.

    Requirement Profiles: Origin of the Light Duration (photoperiod_source)¶

    A phase's requirement profile records where its light duration photoperiod_hours comes from. Only a sourced light duration says something about the plant; the tent hint compares only those.

    Value Meaning

    • GET /api/v1/profiles/requirements/{phase_key} returns the field.

    • Existing installations need no migration: at start-up the seed loaders write sourced into every profile whose light duration a species profile names. Other profiles keep their origin.

    Tent hint in GET /api/v1/t/{slug}/locations/{key}/summary. tent_hints[] forms groups (groups[]) only from light durations with sourced. Plants with generated, default, null or without a profile count as unknown (unknown_plant_count, the first five in unknown_plant_names). Two groups at least one hour apart give tent.photoperiod_conflict (warning); otherwise at least two plants, at least one of them unknown, give tent.photoperiod_unknown (info). Plants in a young phase are not counted.

    Species: Language-Tagged Common Names (common_names_i18n)¶

    Species also carry their common names grouped by language, so the matching name can later be picked per UI language.

    Fields¶

    Field Type Meaning
    common_names list[string] Flat list of all names in all languages — basis for search, forms and CSV import. Unchanged.
    common_names_i18n object (language code → list[string]) Names per language in preference order, the first name is the preferred one. Keys in use today: de, en. Default {}. 
    {
  "scientific_name": "Solanum lycopersicum",
  "common_names": ["Tomate", "Tomato"],
  "common_names_i18n": { "de": ["Tomate"], "en": ["Tomato"] }
}

    Rules¶

    • Every name in common_names_i18n must also be in common_names. The map assigns existing names to a language and never introduces a name of its own. A request that violates this gets 422; the name is never appended silently.
    • Keys are lowercase language codes with 2–3 letters (de, en, fil); other keys give 422.
    • Names are stripped of surrounding whitespace, an empty name gives 422. Duplicate names within one language are dropped, a language left without names is omitted.

    Writing¶

    POST /api/v1/species and PUT /api/v1/species/{key} accept common_names_i18n as an optional field:

    Request Effect
    POST without the field The species is created with {}.
    PUT without the field The stored map is kept. Names you remove from common_names in this PUT also disappear from the map.
    PUT with {} The map is cleared.
    PUT with a map The map is replaced by the one sent (rules above).

    Reading¶

    GET /api/v1/species (and the single-species read) returns common_names_i18n. The same field is part of the species summaries in plant instances (as species_common_names_i18n or common_names_i18n in the species object), planting runs, companion-planting compatibility and the species lists of phase sequences and phase definitions.

    Catalogue Data¶

    The shipped global catalogue (213 species) carries German and English names derived from the plant fact sheets. Existing installations get them at start-up through the seed sync; no migration is needed. The sync only touches rows of the global catalogue; species owned by a tenant are never touched.

    Display Rule¶

    The name shown is the one in the UI language, else the German one, else the scientific name. For a species without an assignment ({}, for example a species a tenant created or imported via CSV), it is the first entry of common_names. For a species with an assignment the first entry is not a valid basis, because the order of the list carries no language.

    Season & Overwintering Automation¶

    These endpoints read the automatically computed season state of a site and the automatically materialised overwintering profile of a plant. Both are derived without user interaction as soon as a plant is assigned to a frost-exposed location — by default, a location on an outdoor, greenhouse, or balcony site (OVERWINTERING_SITE_TYPES), or a location with a manual frost-exposure override on a site of another type (see Setting Frost Exposure for a Location) — on plant creation, on a site change, and additionally as a safety net from the daily season evaluation run — see Season Automation and Overwintering in the user guide.

    All endpoints are under the tenant-scoped path /api/v1/t/{tenant_slug}/ and require a valid JWT token.

    GET /api/v1/t/{tenant_slug}/plants/{plant_key}/overwintering/status

    Additive, read-only companion to GET .../overwintering: always returns 200, even without a profile at all — useful for the plant detail page to distinguish "winter-hardy", "protection needed, plan pending", and "site not frost-exposed" without abusing the profile endpoint's 404 case for that.

  "hardiness_light": "yellow",

    Field Meaning
    has_profile Whether an overwintering profile is already materialised.
    hardiness_light Winter-hardiness rating (green, yellow, red), or null if it cannot be determined (e.g. missing species or site assignment).

    HTTP Status Meaning

    POST /api/v1/t/{tenant_slug}/plants/{plant_key}/overwintering/reset

    Resets user_overridden to false and re-materialises the profile fully from the species profile and the site's winter-hardiness rating.

    Error Codes: 404 if the plant or profile is not found or does not belong to the tenant.

    Plant Identification: Reference Image Contribution (Self-Hosted Recognition)¶

    When creating a plant from a photo identification, a user can optionally contribute the identification photo as a training reference for the self-hosted DINOv2 recognition (see Assigning the Photo to the New Plant — User Guide). 

    POST /api/v1/t/{tenant_slug}/identification/reference

    Requires a valid JWT token and at least the tenant role grower. Only available when self-hosted DINOv2 recognition is active (INFERENCE_SERVICE_ENABLED=true) — the external Pl@ntNet path has no local reference index.

    Request Body: multipart/form-data

    Field Type Required Description
    image file Yes JPEG or PNG image, maximum IDENTIFICATION_MAX_IMAGE_SIZE_MB
    species_key string Yes Resolved species key the reference image is attached to

    No scientific_name field

    The endpoint does not expect a scientific_name form field. The scientific name is derived server-side from the species_key record; any value sent alongside it is ignored.

    Response (202 Accepted): ReferenceContributionResponse

    {
  "accepted": true,
  "pending_review": true,
  "species_key": "species/123",
  "dim": 768
}
    Field Type Meaning
    accepted boolean Whether the contribution was accepted and indexed
    pending_review boolean true while the contribution is quarantined (is_active=false) and does not yet affect other users' active recognition. Becomes false only after a platform admin approves it.
    species_key string The species key the reference image was attached to
    dim integer | null Dimensionality of the computed embedding vector

    Error Codes:

    HTTP Status Meaning
    403 Active tenant role below grower (e.g. viewer)
    403 The reference_contribution consent is missing or was revoked (CONSENT_REQUIRED)
    404 species_key does not reference a known species
    409 Self-hosted recognition is not enabled (INFERENCE_SERVICE_ENABLED=false)
    409 Contributions are disabled in Light mode (REQ-034 §4.1)
    413 Image exceeds IDENTIFICATION_MAX_IMAGE_SIZE_MB
    415 Content-Type is neither image/jpeg nor image/png
    422 Image cannot be decoded (corrupt or not a valid image format)
    429 Daily contribution quota (REFERENCE_CONTRIBUTION_RATE_LIMIT_PER_USER_DAY) exhausted

    Security model (quarantine, provenance, dedup)

    Every contribution is stored with source="user_contributed", is_active=false, and the contributing user and tenant as provenance — it therefore does not affect other tenants' recognition until a platform admin has reviewed it. The dedup key (source_record_id) is derived from the tenant, the contributing user, and the SHA-256 hash of the normalized image: re-submitting the same photo updates your own row instead of creating another one. If a different person contributes the same image — even across tenants — they get their own row as of issue #1770; before that, a plain image hash as the key made such a contribution land on the first contributor's row, so that person's erasure also removed the other person's contribution, and the second person's own erasure never reached it. The original image itself is never persisted — only the embedding.

    CV Disease Diagnosis ¶

    Photo-based condition diagnosis (disease, nutrient deficiency, and — as a secondary category — pest) from a leaf photo, distinct from species identification (Plant Identification) and from the dedicated Pest Detection: this diagnosis answers "what is wrong with the plant?", not "which species/pest is this?". Recognition runs self-hosted in the inference service; the uploaded photo is stripped of EXIF metadata server-side and is never persisted — only a SHA-256 fingerprint is kept (image_deleted_at is set on every response).

    All endpoints live under the tenant-scoped path /api/v1/t/{tenant_slug}/cv-diagnosis/ and require a valid JWT token. Read endpoints (/status, /history) need no special tenant role; write endpoints (/diagnose, /diagnose/{request_key}/confirm) require at least the grower role.

    Always a hypothesis — never an automatic treatment

    Every response carries a never-empty disclaimer field. A CV diagnosis never automatically triggers a treatment and does not bypass any pre-harvest interval gate (see Integrated Pest Management (IPM)) — POST .../confirm creates at most an IPM inspection suggestion that you review and confirm yourself.

    Post-Harvest¶

    All endpoints live under the tenant-scoped path /api/v1/t/{tenant_slug}/post-harvest/ and require a valid JWT token. Read endpoints accept any active membership; write endpoints require at least the grower role; deleting a batch is admin-only.

    Method & Path Description Minimum role
    GET /post-harvest List the tenant's batches (optionally filtered by harvest_batch) any membership
    POST /post-harvest/start-drying Take a harvest batch into post-harvest processing (stage "drying") grower
    GET /post-harvest/{key} Batch details incl. the latest drying measurement and open mold-alert count any membership
    POST /post-harvest/{key}/advance Advance the batch to the next stage (forward, one step) grower
    POST /post-harvest/{key}/drying-progress Record a weight measurement (optionally also water activity, CO₂, snap-test result) grower
    GET /post-harvest/{key}/drying-progress List all drying measurements of the batch any membership
    POST /post-harvest/{key}/observations Record an environmental observation (may auto-raise a mold alert) grower
    GET /post-harvest/{key}/observations List all environmental observations of the batch any membership
    GET /post-harvest/{key}/mold-alerts List the batch's mold alerts any membership
    DELETE /post-harvest/{key} Delete a batch admin

    Stage state machine: drying → curing → stored → released — forward only, one step per call. The drying → curing transition additionally requires dryness_progress_percent >= 95.

    Error codes:

    HTTP status Meaning
    403 Active tenant role below the required minimum role
    404 Batch not found or does not belong to the tenant
    422 Invalid stage transition (backward, skip, or drying progress < 95% on drying → curing), or current_weight_g exceeds the batch's start weight

    Safety guarantees¶

    Value envelope: every command, rule hit, schedule hit and override passes through the same backend chokepoint. A numeric value for an actuator without a configured min_value/max_value is refused (422 for a direct command or override; the affected actuator is skipped and logged for the automatic control loop). If an envelope is configured, every value is automatically clamped into [min_value, max_value] — non-finite values (NaN/Infinity) are likewise never passed through unchanged.

    Time-limited override: POST /actuators/{key}/override requires expires_at as a mandatory field. An expires_at that already lies in the past is rejected with 422 — there is no implicit default duration.

    POST /api/v1/t/my-garden/actuators/act_42/override
{
  "expires_at": "2026-07-11T10:00:00Z",
  "override_state": "on",
  "reason": "Manual ventilation before the weekend"
}

    Response (422) when expires_at has already passed:

    {
  "error_id": "err_...",
  "error_code": "VALIDATION_ERROR",
  "message": "Manual override expires_at must be in the future.",
  "details": [],
  "timestamp": "2026-07-11T09:00:00.000000+00:00",
  "path": "/api/v1/t/my-garden/actuators/act_42/override",
  "method": "POST"
}

    Emergency stop — per-actuator fault tolerance: POST /emergency-stop handles every affected actuator in isolation. If switching a single actuator fails (e.g. Home Assistant unreachable), the call is not aborted — the response lists successfully switched (stopped, forced_on) and failed (failed) actuator keys separately:

    {
  "scenario": "fire_alarm",
  "stopped": ["act_1", "act_3"],
  "forced_on": [],
  "failed": ["act_2"]
}

    Phase Definitions: Plants & Species per Phase ¶

    Two thin, read-only endpoints feed the two additional lists on the phase-definition detail page: which of your own plants are currently in a phase, and which species traverse that phase in the global catalog.

    List Species for a Phase Definition (Global)¶

    Returns all species from the global catalog whose phase sequence includes the given phase definition. No tenant prefix — reference data like botanical families or the hardiness-zone catalog.

    GET /api/v1/phase-definitions/{key}/species

    Requires a valid JWT token; no separate role restriction.

    Path parameter: key — the phase definition's key.

    Response (200): a list of PhaseDefinitionSpeciesResponse. Empty if no species traverses this phase (no 404).

    [
  {
    "key": "species/123",
    "scientific_name": "Solanum lycopersicum",
    "common_names": ["Tomate", "Tomato"],
    "common_names_i18n": { "de": ["Tomate"], "en": ["Tomato"] },
    "typical_duration_days": 30,
    "illustration": "phases/flowering.svg"
  }
]
    Field Type Meaning
    key string The species' key
    scientific_name string Scientific (binomial) name
    common_names list[string] Common names
    common_names_i18n object Common names per language code, see Species: Language-Tagged Common Names
    typical_duration_days integer This phase's typical duration for the species — the species-specific override (override_duration_days) from the phase-sequence entry when set, otherwise the phase definition's default
    illustration string The phase definition's own illustration path (no per-species illustration yet)

    If a species is linked to the same phase definition through more than one phase sequence, it appears only once (de-duplicated by species key); a species-specific override, where set, takes precedence over the definition's default.

    List the Tenant's Active Plant Instances in a Phase Definition¶

    Returns the calling tenant's active plant instances whose current phase resolves to the given phase definition. Tenant-scoped (SEC-001) — an empty tenant context is rejected server-side rather than returning another tenant's data.

    GET /api/v1/t/{tenant_slug}/plant-instances/by-phase-definition/{phase_definition_key}

    Requires a valid JWT token and an active tenant membership; any role may read.

    Response (200): PlantInstancesInPhaseResponse. items is empty if none of the tenant's active plants are in this phase (no 404).

    {
  "total": 2,
  "items": [
    {
      "key": "plant_instances/101",
      "instance_id": "T3-01",
      "plant_name": "Balcony Tomato",
      "species_key": "species/123",
      "species_scientific_name": "Solanum lycopersicum",
      "species_common_names": ["Tomato"],
      "species_common_names_i18n": { "en": ["Tomato"] },
      "location_key": "locations/5",
      "location_name": "South Balcony",
      "slot_key": "slots/12",
      "slot_label": "Row 2, Pot 3",
      "current_phase_key": "phase_sequence_entries/456",
      "current_phase_started_at": "2026-06-20T08:00:00Z"
    }
  ]
}
    Field Type Meaning
    total integer Total number of plant instances returned
    items[].current_phase_key string | null Raw value of PlantInstance.current_phase_key — usually a PhaseSequenceEntry key; for older records it may still be a legacy GrowthPhase key
    items[].current_phase_started_at datetime | null Timestamp of the last phase transition — the basis for the "days in phase" count computed client-side on the detail page

    "Active" means removed_on == null — removed plants (see Growth Phases — User Guide: Removing a Plant) do not appear here. A plant is matched to the phase definition via its current phase-sequence assignment (PhaseSequenceEntry.phase_definition_key); for legacy data without a phase sequence, a fallback via the shared canonical phase name of a legacy GrowthPhase additionally applies.

    No days_in_phase field in the response

    Days in phase are deliberately not returned by the backend; the UI derives them from current_phase_started_at instead, so the value stays current without a re-fetch.

    Route order: /by-phase-definition/{phase_definition_key} is declared before /{key} in the router so the literal path is not accidentally captured as a plant key (the same pattern used for /survival-stats above).

    Plans and quotas of a tenant ¶

    Every tenant points at exactly one plan with plan_key. A plan sets a limit per quota or leaves it empty (null = the server setting). The seeded plan standard leaves everything empty and is the plan of every tenant nothing else is assigned to. The responses of GET /api/v1/tenants/{slug} and GET /api/v1/admin/platform/tenants additionally carry plan_key.

    Quota (dimension) Server setting when null 0 means Refusal
    members TENANT_MAX_MEMBERS_CEILING (never above it) — (at least 1) 422 MEMBER_LIMIT_REACHED
    service_accounts TENANT_MAX_SERVICE_ACCOUNTS — (at least 1) 422 SERVICE_ACCOUNT_LIMIT_REACHED
    storage_mb STORAGE_TENANT_QUOTA_MB unlimited 409 STORAGE_QUOTA_EXCEEDED
    photos_per_instance STORAGE_MAX_PHOTOS_PER_INSTANCE unlimited 409 PHOTO_QUOTA_EXCEEDED
    ai_calls_per_user_day AI_BUDGET_USER_CALLS_PER_DAY budget off 429 AI_BUDGET_EXCEEDED
    ai_calls_per_tenant_day AI_BUDGET_TENANT_CALLS_PER_DAY budget off 429 AI_BUDGET_EXCEEDED
    ai_tokens_per_tenant_day AI_BUDGET_TENANT_TOKENS_PER_DAY budget off 429 AI_BUDGET_EXCEEDED

    0 means unlimited, not \"nothing allowed\"

    For storage_mb and photos_per_instance, 0 lifts the limit entirely; for the three AI budgets, 0 switches the budget off — again no limit. A plan therefore cannot set these dimensions to "none at all". The plan response lists such dimensions in the field unlimited, and the security audit marks a change to 0 as to_unlimited.

    Every quota has an upper bound (e.g. storage_mb at most 10,000,000, ai_tokens_per_tenant_day at most 10¹²); above it the API answers 422. The effective member limit is min(max_members, plan.members ?? ceiling, TENANT_MAX_MEMBERS_CEILING). The platform tenant always follows the server settings and takes no plan (422). A tenant whose plan document is missing or corrupt falls back to the default plan, then to the server setting, never to "unlimited"; a corrupt plan is also left out of the plan listing.

    Read a tenant's plan and usage¶

    GET /api/v1/tenants/{slug}/entitlements — every member. ai_calls_per_user_day.used is your own usage; service_accounts and ai_tokens_per_tenant_day are listed for a lead only. limit: null = unlimited, used: null = counted per plant or not readable right now.

    {"dimension": "storage_mb", "limit": 2048, "used": 731},
    {"dimension": "photos_per_instance", "limit": 50, "used": null},
    {"dimension": "ai_calls_per_user_day", "limit": 50, "used": 3},
    {"dimension": "ai_calls_per_tenant_day", "limit": 500, "used": 41}
  ]
}

    Method Path Effect
    GET /api/v1/admin/platform/plans every plan with tenant_count
    POST /api/v1/admin/platform/plans create a plan (201; 409 for a taken key; 422 out of range or members above the ceiling)
    PATCH /api/v1/admin/platform/plans/{plan_key} change name, description, single quotas (name: null is 422); is_default: true makes it the default of new tenants

    key matches ^[a-z][a-z0-9_-]{1,39}$ and is immutable. Light mode has none of these routes.

    Exporting and importing a tenant ¶

    Steps, archive content and refusals are described in the runbook Exporting and importing a tenant. All routes exist in full mode only; none accepts an API key or a service account (403).

    Method Path Who Effect
    POST /api/v1/tenants/{slug}/exports lead ∧ management + confirmation (tenant_export) request an export (202); in active and pending_deletion. 409 EXPORT_ALREADY_RUNNING while one runs; 429 from the TENANT_EXPORTS_PER_DAY+1st in 24 h; an unknown slug and a missing permission are the same 403
    GET /api/v1/tenants/{slug}/exports lead ∧ management own exports, newest first (paginated)
    GET /api/v1/tenants/{slug}/exports/{export_key}/download whoever requested it the archive as ZIP; 404 after expiry (RETENTION_EXPORT_FILE_RETENTION_HOURS)
    POST /api/v1/admin/platform/tenants/{key}/exports platform admin + confirmation export in every state but deleted
    GET /api/v1/admin/platform/tenants/{key}/exports (…/{export_key}/download) platform admin own exports or the archive
    POST /api/v1/admin/platform/tenant-imports platform admin + confirmation (tenant_import, target archive:<the first 32 hex digits of the file's SHA-256>, checked before the file is read) the archive as multipart/form-data (archive, optional member_mapping as JSON {"<old user_key>": {"email": "…", "role": "lead\|grower\|viewer", "admin_scopes": […]}}, plan_key, confirmation fields); 202, verified says whether this installation signed the archive. Refused before any write with 422 and the codes IMPORT_FORMAT_UNSUPPORTED, IMPORT_CHECKSUM_MISMATCH, IMPORT_UNDECLARED_REFERENCE, IMPORT_MISSING_CATALOG_ENTRIES (listed in details), IMPORT_MEMBER_NOT_FOUND; 413 above TENANT_IMPORT_MAX_UPLOAD_MB
    GET /api/v1/admin/platform/tenant-imports/{import_key} platform admin state and report (report: count per collection), target_tenant_key, verified

    The body carries the confirmation as for a deletion (current_password, step_up_code or step_up_token). An export request (status: pending → running → completed / failed with failure_reason too_large, internal_error, storage_unavailable, tenant_not_exportable → expired) names its size (size_bytes), rows per archive part (counts) and expires_at. Security log: tenant_export_requested, tenant_export_downloaded (every download), tenant_import_requested, tenant_imported. An imported tenant is in the state importing until its last row is written and reachable for nobody.

    Organizations per account¶

    POST /api/v1/tenants refuses once the account owns TENANT_MAX_ORGANIZATIONS_PER_USER organizations (counted in every state but deleted): 422 ORGANIZATION_LIMIT_REACHED (until now 422 VALIDATION_ERROR). This is a limit of the account, not a plan quota.
