# Python Backend Dependency-Management Audit

- **Issue:** nolte/kamerplanter#566
- **Scope:** `src/backend/` Python dependency declaration, pinning, consumption and update flow.
- **Type:** Investigation / audit only — no code, Dockerfile, CI, Renovate or dependency changes were made.
- **Baseline commit:** `f8d06ad58` (develop tip, PR #563 already merged). All claims below were re-verified against the live files in this worktree.
- **Normative reference:** `spec/nfr/NFR-009_Dependency-Management.md` (esp. §§2.1, 2.3, 4.1, 4.3, 5.2, 6.1).

---

## 1. Summary / Verdict

**There is no single source of truth today.** "Truth" is split between two files that no process keeps consistent:

- **Every runtime/CI consumer** (the production image, both CI jobs, the dev image) installs from **`pyproject.toml`** via `pip install .` / `pip install -e ".[dev]"`. These read the *abstract* `[project].dependencies` — `>=` lower bounds **with no upper bound** — so pip resolves whatever is newest on PyPI **at build time**. The build is therefore **not reproducible**.
- **Renovate** manages only the compiled locks **`requirements.txt`** / **`requirements-dev.txt`** through the `pip_requirements` manager. Those files are pinned (`==`) but are **read by nobody** — the Dockerfile copies them in via `COPY . .` yet never runs `pip install -r requirements.txt`.

The consequence is the exact class of failure PR #563 had to repair by hand: Renovate moves a pin in `requirements.txt`, nothing consumes or recompiles it, and the lock drifts internally until a manual `pip-compile` re-sync. The lock is, in the words of the prior incident note, a *decorative lock*.

**What #563 already fixed:** `requirements.txt` now carries a genuine `pip-compile` autogenerated header, and `requirements-dev.txt` now exists (the issue body's claim that it was missing is stale). Both are real, freshly-compiled locks again. **What remains unfixed is architectural:** no consumer installs from the lock, Renovate targets the lock rather than the PEP 621 source, and there is no automated recompile step — so the drift surface #563 closed will reopen on the next Renovate pin bump.

**Recommended target: Option A** — keep `pyproject.toml` as the abstract single source of truth, generate the locks with `pip-compile`, make **both** the prod Dockerfile and CI install `-r requirements*.txt`, and switch Renovate to the PEP 621 manager plus a `pipCompileOutput` post-update step so one PR moves the source constraint *and* recompiles the lock atomically. This is precisely the design NFR-009 §6.1 already prescribes.

## 3. "Where Truth Lives" Matrix

| Consumer | Authoritative file today | Pinned? | Can drift from the others? |
|----------|--------------------------|---------|----------------------------|
| **(a) Running prod image** | `pyproject.toml` `[project].dependencies` (`Dockerfile:52`, `docker-publish.yml:103-106`) | **No** — `>=`, unbounded, resolved at build time | Yes. Two builds of the same commit can ship different versions; neither matches `requirements.txt`. |
| **(b) CI test runs** | `pyproject.toml` `[project.optional-dependencies].dev` (`backend.yml:34,51`) | **No** — `>=`, resolved at CI time | Yes. CI can pass against versions the lock never saw, and vice-versa. |
| **(c) pip-audit** | — (does not exist, item #13) | — | N/A — no CVE gate on Python deps at all. |

The four consumers disagree on which file is authoritative. (a) and (b) trust `pyproject.toml`; (d) trusts `requirements.txt`; (c) is missing. That divergence is the defect.

## 4. Drift Surface — Step-by-Step (reproducing the #563 class)

`pydantic-core` is a **transitive** dependency (pulled in by `pydantic`, itself pulled in by `fastapi`). It appears **only** in the lock (`requirements.txt:178 pydantic-core==2.46.4`), never in `pyproject.toml`.

1. Renovate's `python fastapi-stack` rule (`renovate.json5:53-64`, `matchManagers: ['pip_requirements']`, `matchPackageNames` includes `pydantic-core`) sees a newer `pydantic-core` on PyPI and opens a PR bumping the single line `pydantic-core==X` in `requirements.txt`.
2. There is **no** `postUpdateOptions: ['pipCompileOutput']` and **no** `lockFileMaintenance` (item #12), so Renovate does **not** re-run `pip-compile`. It edits one pin in isolation. `pydantic` (line 173) and every other transitive pin stay put, so the lock is now internally inconsistent (a `pydantic-core` version that `pip-compile` would not have paired with the frozen `pydantic`).
3. `pyproject.toml` is untouched — the abstract constraint is still `pydantic[email]>=2.10.0` (`:10`), which already admits the new version, so nothing there changes either.
4. **The bumped pin never reaches any artifact.** The prod image (`Dockerfile:52`, `pip install .`) and both CI jobs (`backend.yml:34,51`, `pip install -e ".[dev]"`) resolve `pydantic-core` freshly from PyPI via the `pyproject` `>=` bound; they never read `requirements.txt`. The Renovate PR is therefore cosmetic: it neither hardens nor reproduces the build.
5. The inconsistency accumulates until a human notices and runs `pip-compile` by hand to re-synchronise the whole lock — which is exactly **PR #563** (`f8d06ad58` / `c5b1efa5b`, *"recompile backend lockfiles to fix pydantic-core drift"*).

**Root cause:** the file Renovate writes (`requirements.txt`) and the file every consumer reads (`pyproject.toml`) are different, and no automation binds them. A lock only prevents drift if (i) something recompiles it whole on every source change and (ii) the deployed artifact installs *from* it. Neither holds here.

## 6. Recommended Target Model

The tension to preserve: `pyproject.toml` legitimately declares **abstract, direct** dependencies (what the app needs), while `requirements*.txt` is a **pinned, transitive** lock (exactly what to install). These are two different concerns and should **not** be collapsed carelessly. The question is only *which is authoritative* and *who consumes the lock*.

### Option A — pyproject as SSOT + compiled lock consumed everywhere (recommended)

Keep `pyproject.toml` abstract (add the missing upper bounds per MUST #1). Generate `requirements.txt` / `requirements-dev.txt` with `pip-compile`. Then:

- **Prod Dockerfile** installs `-r requirements.txt` (copy the lock first for layer caching), then `pip install --no-deps .` to add the app package itself.
- **CI** installs `-r requirements-dev.txt` for the lint/test/coverage jobs.
- Add `--generate-hashes` to the compile step and `--require-hashes` on install **if feasible** (all wheels available on Python 3.14 — verify; `aquacropeto`, `weasyprint` native deps are the risk).
- **Renovate** switches to the PEP 621 manager for `pyproject.toml` **plus** `postUpdateOptions: ['pipCompileOutput']` (or `lockFileMaintenance`) so a single PR moves the abstract constraint *and* recompiles the pinned lock atomically.

| Criterion | Assessment |
|-----------|------------|
| Reproducibility | Strong — the deployed artifact installs the exact pinned (optionally hashed) set. |
| pip-audit accuracy | Strong — audit runs against the same lock that ships. |
| CI lockfile-integrity | Strong — CI fails if the lock is stale/inconsistent (compile-check in CI). |
| Renovate ergonomics | Strong — one atomic PR per bump; no decorative-lock drift; **directly matches NFR-009 §6.1**. |

Cost: touch Dockerfile, `backend.yml`, `renovate.json5`; validate hash-pinning against native-wheel deps; resolve the §5.2-vs-§2.3 spec contradiction (make §5.2 say `pip install --no-deps .` after `-r requirements.txt`).

### Option B — pyproject-only, drop `requirements.txt`

Delete the locks; Renovate on the PEP 621 manager bumps the `>=` bounds in `pyproject.toml`; everything keeps installing `pip install .`.

| Criterion | Assessment |
|-----------|------------|
| Reproducibility | Weak — transitive deps still float; no pinned set unless bounds are tightened to `==` (which defeats abstract declaration). |
| pip-audit accuracy | Weak — audits a resolved-at-runtime tree, not a committed artifact. |
| CI lockfile-integrity | N/A — nothing to check. |
| Renovate ergonomics | Simple — one file, one manager. |

Verdict: simplest, but concedes reproducible builds — contradicts the issue's stated goal state and NFR-009 §2.3.

### Option C — migrate to `uv` (or Poetry) native lock

Adopt `uv` with `uv.lock` as a single native lock (`uv sync --frozen` everywhere; Renovate has a `uv` manager). Poetry is the analogous alternative.

| Criterion | Assessment |
|-----------|------------|
| Reproducibility | Strong — native, hash-locked, one command. |
| pip-audit accuracy | Strong (export or `uv`-native audit). |
| CI lockfile-integrity | Strong — `--frozen` fails on drift. |
| Renovate ergonomics | Good — but a larger migration; changes local dev, CI, Docker and the build backend at once. |

Verdict: best end-state ergonomics, highest migration cost and blast radius. A reasonable future step, not the minimal fix.

### Recommendation

**Adopt Option A.** It closes all five open NFR-009 deviations with the smallest change, keeps the correct abstract-vs-pinned separation intact, and is the design NFR-009 §6.1 already mandates. Revisit **Option C (`uv`)** later as an ergonomics upgrade once Option A has stabilised the single-source-of-truth invariant.

## 7. Follow-up Implementation Outline (OUT OF SCOPE here)

Implementation belongs to a **separate issue/PR** — this document is analysis only. Suggested sequence for that work:

1. **Tighten `pyproject.toml`** — add upper bounds to `[project].dependencies` / `dev` (MUST #1); recompile both locks.
2. **Consume the lock in prod** — `Dockerfile` prod stage: `COPY requirements.txt .` → `pip install -r requirements.txt` → `pip install --no-deps .` (MUST #4). Evaluate `--require-hashes` against native-wheel deps (`weasyprint`, `psycopg[binary]`, `aquacropeto`).
3. **Consume the lock in CI** — `backend.yml` lint/test + coverage: install `-r requirements-dev.txt`; add a `pip-compile --dry-run`/diff check that fails if the committed lock is stale (MUST #4).
4. **Add the security gates** — a `pip-audit -r requirements.txt` job (PR + push + weekly) and a `pip-licenses` allowlist gate (MUST #5, #6).
5. **Repoint Renovate** — replace the three `pip_requirements` rules with PEP 621 manager rules on `src/backend/pyproject.toml` + `postUpdateOptions: ['pipCompileOutput']` (or `lockFileMaintenance`), preserving the existing grouping (fastapi-stack, minor/patch, major) (MUST #7). Confirm the inherited `gh-plumbing//renovate-configs/common` config does not re-enable a stray `pip_requirements` scan.
6. **Add a regeneration task** — `Taskfile.yaml` `deps:compile` target wrapping the two `pip-compile` commands, so local regeneration is one command, not tribal knowledge (item #14).
7. **Resolve the NFR-009 internal conflict** — reword §5.2 so build verification uses `pip install --no-deps .` after `-r requirements.txt`, removing the §5.2-vs-§2.3 contradiction (item ⚠️ #8).
