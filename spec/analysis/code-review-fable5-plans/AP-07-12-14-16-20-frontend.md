## AP-7 — OAuth-Callback-Sicherheit (FE-S1, FE-S3, FE-S4)

### Ziel & Anforderung

Der OAuth-Login-Abschluss darf kein Access-Token über die URL transportieren oder aus der URL akzeptieren (Token-Injection-/Leak-Vektor), darf keine unvalidierten `error`-Parameter anzeigen und muss Provider-Slugs URL-kodieren. Bezug: REQ-023 (JWT-Access-Token 15 min + HttpOnly-Refresh-Cookie mit Rotation).

### Root-Cause-Analyse (verifiziert)

**Zentrale Erkenntnis — Backend und Frontend sind bereits inkonsistent:**

1. **Backend sendet Fragment, Frontend liest Query.**
   `src/backend/app/api/v1/auth/router.py:196-229` (Callback-Endpoint) macht bereits das meiste richtig:
   - Zeile 227: `_set_refresh_cookie(redirect, raw_refresh, is_persistent=...)` — **das HttpOnly-Refresh-Cookie wird im OAuth-Callback bereits gesetzt** (Pfad `/api/v1/auth`, vgl. Zeile 32-53).
   - Zeile 228: `set_csrf_cookie(redirect)`.
   - Zeile 220-224: Redirect auf `{frontend_url}/auth/callback#access_token=...&expires_in=...` — Token im **URL-Fragment**, nicht im Query-String.

   Das Frontend `src/frontend/src/pages/auth/OAuthCallbackPage.tsx:15-25` liest dagegen `useSearchParams()` (= `location.search`, **Query-String**). Ein Fragment landet dort nie → der reguläre Fluss läuft heute vermutlich in den `oauthNoToken`-Fehler (Zeile 19) bzw. funktioniert nur, wenn ein Token per Query ankommt.

2. **FE-S1 — Token-Akzeptanz aus der URL:** `OAuthCallbackPage.tsx:24-28` nimmt jedes `?access_token=<beliebig>` aus der URL entgegen und schreibt es via `dispatch(setAccessToken(accessToken))` in den Store. Ein Angreifer kann per präpariertem Link (`/auth/callback?access_token=<attacker-token>`) eine Session-Fixation auf ein fremdes Konto auslösen (Login-CSRF-Variante). Zusätzlich: Tokens in URLs landen in Browser-History, Referer-Headern und Proxy-Logs.

3. **FE-S3 — Unvalidierter `error`-Parameter:** `OAuthCallbackPage.tsx:16-21` initialisiert den Fehler-State direkt mit `searchParams.get('error')` und rendert ihn roh in Zeile 42-44 (`<Alert>{error}</Alert>`). React escapet zwar (kein XSS), aber beliebiger Angreifer-Text ist als "offizielle" Fehlermeldung darstellbar (Phishing-Vektor, z. B. `?error=Bitte+loggen+Sie+sich+unter+evil.example+ein`), und die Meldung ist nicht internationalisiert.

4. **FE-S4 — Unkodierter Slug:** `src/frontend/src/pages/auth/LoginPage.tsx:125`:
   ```ts
   window.location.href = `/api/v1/auth/oauth/${p.slug}`;
   ```
   `p.slug` stammt aus der API-Antwort (`getOAuthProviders()`, geladen in Zeile 35) und wird ohne `encodeURIComponent` interpoliert. Bei kompromittiertem/fehlkonfiguriertem Provider-Datensatz sind Pfad-Manipulationen (`../`, `?`, `#`) möglich.

**Vorhandene Bausteine (wiederverwendbar, kein Neubau nötig):**
- `src/frontend/src/store/slices/authSlice.ts:47-51`: `refreshAccessToken`-Thunk existiert, ruft `authApi.refresh()` (`src/frontend/src/api/endpoints/auth.ts:41-43`, `POST /auth/refresh`, Cookie-basiert).
- `src/frontend/src/auth/AuthProvider.tsx:136-174` (`initAuth`): führt beim App-Mount bereits `refreshAccessToken()` → `setAccessToken` → `fetchProfile` aus. **Der Cookie-basierte Bootstrap-Flow existiert also vollständig.**

### Lösungsdesign

**Kernidee: Das Access-Token verschwindet komplett aus der Redirect-URL.** Da das Backend im Callback bereits das Refresh-Cookie setzt, braucht das Frontend auf `/auth/callback` nur den regulären Cookie-Refresh anzustoßen — exakt derselbe Fluss wie `initAuth`.

```
Provider ──302──▶ GET /api/v1/auth/oauth/{slug}/callback
                     │  setzt kp_refresh (HttpOnly) + CSRF-Cookie
                     ▼
                  302 → {frontend}/auth/callback            (ohne Token!)
                     │
                  OAuthCallbackPage: dispatch(refreshAccessToken())
                     │        └─ POST /auth/refresh (Cookie) → access_token
                     ▼
                  setAccessToken → fetchProfile → navigate('/dashboard')
```

Fehlerfall (Provider lehnt ab, State ungültig): Backend redirected mit `?error=<code>` aus einer **festen Code-Menge**; Frontend mappt Codes per Whitelist auf i18n-Keys, unbekannte Codes → generische Meldung.

```ts
import { useState, useEffect, useCallback, useMemo } from 'react';

export interface AsyncOptionsResult<T> {
  options: T[];
  loading: boolean;
  /** True when the load failed — render an error hint instead of an empty list. */
  error: boolean;
  reload: () => void;
}

/**
 * Loads select/autocomplete options with explicit loading/error state.
 * Replaces the silent `.catch(() => {})` pattern (Code-Review FE-L3).
 * `loader` MUST be referentially stable (useCallback in the caller).
 */
export function useAsyncOptions<T>(
  loader: () => Promise<T[]>,
  { enabled = true }: { enabled?: boolean } = {},
): AsyncOptionsResult<T> {
  const [options, setOptions] = useState<T[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState(false);
  const [nonce, setNonce] = useState(0);

  const reload = useCallback(() => setNonce((n) => n + 1), []);

  useEffect(() => {
    if (!enabled) return;
    let cancelled = false;
    setLoading(true);
    setError(false);
    loader()
      .then((items) => { if (!cancelled) setOptions(items); })
      .catch(() => { if (!cancelled) setError(true); })
      .finally(() => { if (!cancelled) setLoading(false); });
    return () => { cancelled = true; };
  }, [loader, enabled, nonce]);

  // FRONTEND.md §6.1: object return MUST be useMemo-stabilised.
  return useMemo(
    () => ({ options, loading, error, reload }),
    [options, loading, error, reload],
  );
}
```

Konsumenten-Muster (Dialog/Autocomplete):
```tsx
const loadSites = useCallback(() => sitesApi.listSites(0, 200).then((r) => r.items), []);
const { options: sites, loading, error } = useAsyncOptions(loadSites, { enabled: open });
// ...
<Autocomplete loading={loading} ... />
{error && <FormHelperText error>{t('errors.optionsLoadFailed')}</FormHelperText>}
```
Neuer i18n-Key `errors.optionsLoadFailed` = "Auswahloptionen konnten nicht geladen werden." (+ EN).

## AP-14 — Hook-Konventionsverstöße & doppelter Interceptor (FE-D1, FE-D2, FE-D3)

### Ziel & Anforderung

`spec/style-guides/FRONTEND.md` §6.1 (Zeilen 341-364): Custom Hooks, die Objekte/Arrays zurückgeben, **müssen** den Return mit `useMemo` stabilisieren (projektweite PFLICHT-Konvention, auch in `~/.claude` MEMORY verankert). Duplizierter Axios-Interceptor-Code wird dedupliziert.

### Root-Cause (verifiziert)

1. **FE-D1 — `src/frontend/src/hooks/usePagination.ts:31-35`:**
   ```ts
   return {
     ...state,
     setPage,
     setRowsPerPage,
   };
   ```
   Neues Objekt bei jedem Render → Konsumenten, die das Objekt in Dep-Arrays legen, re-rendern/re-fetchen unnötig.

2. **FE-D2 — `src/frontend/src/hooks/useApiError.ts:114`:** `return { handleError };` — `handleError` ist zwar `useCallback` (Zeile 11), das umschließende Objekt aber bei jedem Render neu.

3. **FE-D3 — `src/frontend/src/api/client.ts:30-41` und `:63-74`:** Response-Interceptor (ApiError-Envelope-Erkennung) ist für `client` und `tenantClient` zeichengleich dupliziert.

### Lösungsdesign & konkrete Änderungen

#### `hooks/usePagination.ts`

```ts
return useMemo(
  () => ({ ...state, setPage, setRowsPerPage }),
  [state, setPage, setRowsPerPage],
);
```
(`state` ist ein einzelnes useState-Objekt, `setPage`/`setRowsPerPage` sind useCallback-stabil ⇒ Identität ändert sich nur bei echter Paginierungs-Änderung.) Import um `useMemo` ergänzen.

#### `hooks/useApiError.ts`

```ts
return useMemo(() => ({ handleError }), [handleError]);
```

#### `api/client.ts` — Interceptor deduplizieren

```ts
function rethrowApiError(error: unknown): never {
  if (axios.isAxiosError(error) && error.response) {
    const data = error.response.data as ApiErrorResponse;
    if (data?.error_id && data?.error_code) {
      throw new ApiError(data, error.response.status);
    }
  }
  throw error;
}

client.interceptors.response.use((response) => response, rethrowApiError);
// … tenantClient-Request-Interceptor unverändert …
tenantClient.interceptors.response.use((response) => response, rethrowApiError);
```

## AP-16 — Hardcoded Strings, Slice-Fehlertexte, createListSlice (FE-L4, FE-L5, FE-D5)

### Ziel & Anforderung

Keine hartkodierten UI-Strings (i18n-Pflicht, FRONTEND.md §9, Key-Schema `pages.<section>.<key>` / `errors.*`); Redux-Slices speichern keine rohen englischen Fehlertexte; die ~20 strukturell identischen List-Slices erhalten eine Factory.

### Root-Cause (verifiziert)

1. **FE-L4 — Hardcoded Strings:**
   - `pages/admin/AdminEditTenantPage.tsx:193`: `<Alert severity="error">Tenant not found</Alert>`
   - `pages/admin/AdminEditUserPage.tsx:191`: `<Alert severity="error">User not found</Alert>`
   - `pages/pflanzen/CalculationsPage.tsx:166`: `label="Min,Max (pro Zeile)"` (hartkodiertes Deutsch — bricht die EN-Locale)

2. **FE-L5 — rohe englische Slice-Fehlertexte:** Muster `state.error = action.error.message ?? 'Failed to load X'` in mindestens 13 Slices / 20+ Stellen (verifiziert u. a. `speciesSlice.ts:62,74`, `activitiesSlice.ts:56`, `harvestSlice.ts:119,132`, `calendarSlice.ts:122,134,164,177`, `plantingRunsSlice.ts:66`, `ipmSlice.ts:179,195,211`, `tenantSlice.ts:103`, `careRemindersSlice.ts:96`, `feedingEventsSlice.ts:62`, `plantInstancesSlice.ts:56`, `nutrientPlansSlice.ts:69`, `botanicalFamiliesSlice.ts:56,68`). Diese Strings landen via `ErrorDisplay` in der UI; `ErrorDisplay.tsx:6-24` versucht das heute mit fragilen Regex-Patterns (`ERROR_PATTERNS`) rückzuübersetzen — Symptombehandlung.

3. **FE-D5 — Copy-Paste-Slices:** `speciesSlice.ts` (81 Zeilen) ist der Prototyp: State `{items,total,offset,limit,current,loading,error}` + `fetchAll`/`fetchOne`-Thunks + 6 identische extraReducer-Cases. Dasselbe Skelett existiert ~13-mal.

### Lösungsdesign

#### a) Fehler-Konvention: Slices speichern i18n-Keys, nicht Prosa

Slices haben keinen Zugriff auf `t()` (korrekt so — Store bleibt sprachfrei). Konvention: **`state.error` enthält entweder einen i18n-Key (`errors.*`) oder eine bereits nutzerfähige ApiError-Message.** Auflösung geschieht in `ErrorDisplay`:

- `translateError` (`components/common/ErrorDisplay.tsx:17-24`) bekommt als ersten Check:
  ```ts
  if (/^errors\.[a-zA-Z.]+$/.test(error)) return t(error);
  ```
  Die bestehenden `ERROR_PATTERNS` bleiben als Übergangs-Fallback für noch nicht migrierte Slices und rohe Backend-Messages bestehen.
- Neuer generischer Key `errors.loadFailed` = "Die Daten konnten nicht geladen werden." / "Failed to load data." (Entity-spezifische Varianten sind nicht nötig — der Seitenkontext liefert die Entität; wer sie doch braucht, nutzt `errors.loadFailedEntity` mit `{{entity}}` + `entities.*`-Keys, die bereits existieren, `translation.json:384 ff.`).

#### b) `createListSlice`-Factory

Neue Datei `src/frontend/src/store/createListSlice.ts`:

```ts
import { createSlice, createAsyncThunk } from '@reduxjs/toolkit';
import type { ActionReducerMapBuilder } from '@reduxjs/toolkit';

export interface Paginated<T> {
  items: T[];
  total: number;
  offset: number;
  limit: number;
}

export interface ListState<T> {
  items: T[];
  total: number;
  offset: number;
  limit: number;
  current: T | null;
  loading: boolean;
  error: string | null; // i18n key or ApiError message
}

interface ListSliceConfig<T> {
  name: string;
  list: (offset: number, limit: number) => Promise<Paginated<T>>;
  getOne?: (key: string) => Promise<T>;
  /** i18n error key, defaults to 'errors.loadFailed'. */
  errorKey?: string;
  /** Extension point for entity-specific thunks/cases. */
  extraCases?: (builder: ActionReducerMapBuilder<ListState<T>>) => void;
}

export function createListSlice<T>(config: ListSliceConfig<T>) {
  const fetchList = createAsyncThunk(
    `${config.name}/fetchAll`,
    async ({ offset = 0, limit = 50 }: { offset?: number; limit?: number } = {}) =>
      config.list(offset, limit),
  );
  const fetchOne = config.getOne
    ? createAsyncThunk(`${config.name}/fetchOne`, async (key: string) => config.getOne!(key))
    : undefined;

  const slice = createSlice({
    name: config.name,
    initialState: { items: [], total: 0, offset: 0, limit: 50, current: null, loading: false, error: null } as ListState<T>,
    reducers: {
      clearCurrent(state) { state.current = null; },
      clearError(state) { state.error = null; },
    },
    extraReducers: (builder) => {
      builder
        .addCase(fetchList.pending, (s) => { s.loading = true; s.error = null; })
        .addCase(fetchList.fulfilled, (s, a) => { s.loading = false; Object.assign(s, a.payload); })
        .addCase(fetchList.rejected, (s, a) => {
          s.loading = false;
          s.error = a.error.message ?? config.errorKey ?? 'errors.loadFailed';
        });
      // … analoge Cases für fetchOne, wenn vorhanden …
      config.extraCases?.(builder);
    },
  });

  return { slice, fetchList, fetchOne, actions: slice.actions };
}
```

**Design-Entscheidung `a.error.message ?? key`:** ApiError-Messages aus dem Envelope (via `rethrowApiError`, AP-14) sind bereits die beste verfügbare Information und werden von `translateError`-Patterns weiter normalisiert; nur der Fallback wechselt von englischer Prosa auf den i18n-Key. Wer strenger will, dreht auf `config.errorKey` als Immer-Wert — Entscheidung im Pilot-PR treffen und in der Factory einheitlich fixieren.

**Konsumenten-Beispiel (speciesSlice.ts danach, ~15 Zeilen statt 81):**
```ts
const { slice, fetchList, fetchOne, actions } = createListSlice<Species>({
  name: 'species',
  list: (offset, limit) => api.listSpecies(offset, limit),
  getOne: (key) => api.getSpecies(key),
});
export const fetchSpeciesList = fetchList;
export const fetchSpecies = fetchOne!;
export const { clearCurrent, clearError } = actions;
export default slice.reducer;
```
Re-Exports behalten die bisherigen Namen ⇒ **keine Änderung in Pages/Tests nötig** (Action-Type-Strings `species/fetchAll` etc. bleiben identisch).

#### c) Hardcoded Strings

| Stelle | Fix |
|---|---|
| `AdminEditTenantPage.tsx:193` | `{t('pages.admin.tenantNotFound')}` — DE: "Mandant nicht gefunden." |
| `AdminEditUserPage.tsx:191` | `{t('pages.admin.userNotFound')}` — DE: "Benutzer nicht gefunden." |
